# SEC-009.1 — Instalación y uso local de Gitleaks (Windows)

## 1. Objetivo

Esta guía documenta la instalación **manual** de Gitleaks en Windows que el operador ya realizó, para que otros desarrolladores puedan repetirla.

Gitleaks local sirve como **feedback** antes de abrir o actualizar un Pull Request. El **enforcement** oficial es GitHub Actions: el job `secret-scan` (`gitleaks/gitleaks-action@v3`) es Required Status Check en el Ruleset de `main` y bloquea el merge si falla. Instalar Gitleaks en la máquina no modifica el CI ni sustituye ese check.

Gitleaks es una herramienta externa de desarrollo. **No** forma parte del runtime de producción y **no** se instala como dependencia npm.

## 2. Descarga

No se usó Scoop ni ningún gestor de paquetes.

Descargar el binario oficial desde GitHub Releases:

https://github.com/gitleaks/gitleaks/releases

Seleccionar un artefacto **Windows x64** de una release compatible y verificada. La arquitectura debe coincidir con la del equipo. En la mayoría de PCs Windows actuales corresponde `windows_x64`.

No es necesario fijar una versión concreta en esta guía. Usar una release Windows x64 que funcione en el equipo.

## 3. Instalación manual

Crear (si no existe) la carpeta de herramientas locales:

```text
C:\Tools\gitleaks
```

Extraer el ejecutable ahí. La estructura final debe ser:

```text
C:\Tools\gitleaks\gitleaks.exe
```

No colocar `gitleaks.exe` dentro del repositorio de Nómadas Tour.

## 4. PATH de usuario

Agregar **la carpeta** `C:\Tools\gitleaks` al PATH del **usuario**, no al PATH global del sistema. No agregar `gitleaks.exe` como entrada del PATH.

Pasos en Windows:

```text
Inicio
→ Buscar "Variables de entorno"
→ Editar las variables de entorno del sistema
→ Variables de entorno
→ Variables de usuario
→ Path
→ Editar
→ Nuevo
```

Agregar:

```text
C:\Tools\gitleaks
```

## 5. Reinicio de terminales

No hace falta reiniciar Windows.

Cerrar las terminales que ya estaban abiertas y abrir una nueva para que hereden el PATH actualizado.

**Cursor:** si Cursor ya estaba abierto antes de cambiar el PATH, su terminal integrada puede conservar el PATH anterior. En ese caso, cerrar y volver a abrir Cursor.

## 6. Verificación

Desde una terminal nueva:

```powershell
gitleaks version
```

Debe mostrar la versión instalada.

Si PowerShell responde:

```text
gitleaks : The term 'gitleaks' is not recognized...
```

comprobar:

1. Que `C:\Tools\gitleaks\gitleaks.exe` exista.
2. Que `C:\Tools\gitleaks` esté en el PATH de usuario (carpeta, no el `.exe`).
3. Que se haya abierto una terminal nueva después de cambiar el PATH.
4. Si Cursor estaba abierto antes del cambio, reiniciar Cursor.

Comprobación directa del ejecutable (aísla PATH vs instalación):

```powershell
& "C:\Tools\gitleaks\gitleaks.exe" version
```

Si este comando funciona y `gitleaks version` no, el problema es el PATH.

## 7. Scan local

Desde la raíz del repositorio (`D:\nomadas-tour`):

```powershell
gitleaks git --redact .
```

`--redact` evita imprimir en la terminal los valores detectados.

Resultado real del operador:

```text
136 commits scanned.
scanned ~12068446 bytes (12.07 MB) in 1.89s
no leaks found
```

El número de commits es informativo y puede variar según el historial disponible en el clone local.

## 8. Qué hacer si aparecen findings

**No modificar `.gitleaks.toml` de inmediato.**

| Tipo                                                                                                    | Acción                                                                     |
| ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Secreto real (service role, API key, JWT secret, Resend, AWS, private key, credencial de base de datos) | No allowlistear. Investigar, quitar del código y rotar cuando corresponda. |
| Falso positivo                                                                                          | Contrastar con las reglas específicas de `.gitleaks.toml`.                 |
| Cualquier finding                                                                                       | Nunca crear exclusiones amplias de directorios para ocultarlo.             |

## 9. Relación con CI

```text
Gitleaks local = feedback
secret-scan en GitHub Actions = enforcement
```

El flujo de enforcement permanece:

```text
Pull Request
    ↓
GitHub Actions
    ↓
secret-scan
    ↓
gitleaks/gitleaks-action@v3
    ↓
PASS → continúa
FAIL → Required Status Check falla
    ↓
GitHub Ruleset bloquea el merge
```

La instalación local no cambia el workflow ni sustituye el Required Status Check.

## 10. Archivos `.env`

Los archivos locales cubiertos por `.gitignore` (por ejemplo `.env`, `.env-example`, `backend/.env`, `backend/.env-example`) están destinados a permanecer fuera del repositorio.

El CI y Gitleaks en GitHub trabajan sobre el **checkout de Git**, no sobre copias que existan solo en la máquina del desarrollador. No hace falta sanitizar ni eliminar `.env` locales para ejecutar el scan.

Los ejemplos versionados deben contener únicamente placeholders.

## 11. Gitleaks no es dependencia npm

No agregar Gitleaks a:

```text
package.json
package-lock.json
backend/package.json
backend/package-lock.json
```

En GitHub el scanner se ejecuta con:

```yaml
uses: gitleaks/gitleaks-action@v3
```

## 12. Comandos de referencia

```powershell
gitleaks version
gitleaks git --redact .
gitleaks protect --staged --redact
```

Antes de un PR: tests y typecheck/build del proyecto, luego Gitleaks local, luego confirmar que `secret-scan` pase en GitHub.

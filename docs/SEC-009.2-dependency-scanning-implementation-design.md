## 1. Executive Summary

SEC-009.2 **implements** dependency vulnerability scanning in CI using `npm audit`. HIGH and CRITICAL findings fail the job. MODERATE and LOW do not fail `--audit-level=high`.

**Live (after implementation):** `audit:deps` in root `package.json`; leaf job `dependency-scan` in `.github/workflows/ci.yml`; root and backend **0 vulnerabilities** at `--audit-level=high`. Required Status Check is **not** configured yet — the job does **not** yet block merge via Ruleset.

**Historical (design-time inventory below in §3):** 10 HIGH + 1 MODERATE. Remediation (`next` 16.2.9 → 16.3.2 and remaining fixes) was completed and committed **before** the CI gate landed. The gate implementation did not run `npm audit fix` and did not change lockfiles.

Key design decisions:

| Decision                 | Choice                                                     | Rationale                                                                                             |
| ------------------------ | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Tool                     | `npm audit`                                                | Built into npm; no additional dependencies; sufficient for Node.js projects                           |
| Scope                    | Root + backend (two separate invocations)                  | Independent lockfiles; `npm audit` in root does NOT cover `backend/`                                  |
| Severity                 | `--audit-level=high` (blocks on HIGH + CRITICAL)           | Industry standard; moderate/low are informational                                                     |
| CI job                   | `dependency-scan` (single job, two steps)                  | Simple; leaf job; clear Required Status Check                                                         |
| Fix strategy             | `npm audit fix` for safe fixes; manual for semver-breaking | Avoids `--force` in CI; operator controls lockfile changes                                            |
| Script                   | `audit:deps` in root `package.json`                        | Local reproducibility; single command for both scopes                                                 |
| Dependabot / OSV-Scanner | **Not in MVP**                                             | `npm audit` covers the immediate need; Dependabot adds PR noise; OSV-Scanner adds external dependency |

**Intended merge-block after Required Status Check:** Any PR that introduces a HIGH or CRITICAL dependency vulnerability fails `dependency-scan`. **Today the job is in CI; the Ruleset Required Status Check is still pending.**

## 4. Root vs Backend Audit Strategy

### 4.1 Why two separate invocations

`npm audit` operates on the lockfile in the current working directory. Running `npm audit` at the repo root audits `package-lock.json` only. It does NOT recurse into `backend/`.

The project has two independent npm projects:

- Root: `package.json` + `package-lock.json` (Next.js frontend)
- Backend: `backend/package.json` + `backend/package-lock.json` (Express/TypeScript backend)

Each has its own lockfile with different dependency trees. Both must be audited independently.

### 4.2 Verified commands

```powershell
# Root audit
npm audit --audit-level=high
# Exit code: 1 (7 high found)

# Backend audit
npm audit --prefix backend --audit-level=high
# Exit code: 1 (3 high found)
```

### 4.3 Why not a consolidated script for CI

A consolidated shell script (e.g., `scripts/audit.sh`) would add indirection without benefit. CI steps are already declarative and visible in the workflow YAML. Two `run:` steps in a single job are simpler, more transparent, and easier to debug than a script.

However, a root `npm run audit:deps` script IS recommended for local developer convenience (see §9).

## 5. npm audit Evaluation

### 5.1 Strengths

| Strength            | Detail                                                          |
| ------------------- | --------------------------------------------------------------- |
| Built-in            | No installation required; ships with npm                        |
| Exit codes          | Returns 1 on findings above threshold — perfect for CI gates    |
| `--audit-level`     | Granular control: `info`, `low`, `moderate`, `high`, `critical` |
| `--json`            | Machine-readable output for future automation                   |
| Lockfile-based      | Scans actual installed versions, not just declared ranges       |
| No external service | No API keys, no SaaS dependency, no data leaves the machine     |

### 5.2 Limitations

| Limitation                           | Impact                                                            | Mitigation                                                                                 |
| ------------------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Advisory database freshness          | npm advisory DB may lag behind GitHub Advisory Database           | Acceptable for MVP; Dependabot/OSV-Scanner can supplement later                            |
| No license scanning                  | Cannot detect license compliance issues                           | Explicitly out of scope for SEC-009.2                                                      |
| No SBOM generation                   | Cannot produce Software Bill of Materials                         | Explicitly out of scope                                                                    |
| False positives on devDependencies   | May flag vulnerabilities in packages only used during development | Use `--omit=dev` option if needed; or accept that devDep vulns still matter (supply chain) |
| `npm audit fix --force` in CI        | Can break things by installing outside declared ranges            | Never use `--force` in CI; operator controls lockfile changes                              |
| No fix available for some advisories | Some vulnerabilities have no upstream fix yet                     | Design §10 defines the exception/remediation policy                                        |

### 5.3 Why not Dependabot

| Factor                 | Dependabot                                                   | npm audit in CI                       |
| ---------------------- | ------------------------------------------------------------ | ------------------------------------- |
| Setup                  | Requires `.github/dependabot.yml` + GitHub Advanced Security | Zero config — built into npm          |
| PR noise               | Creates individual PRs for each update                       | Single CI job; no PR noise            |
| Update type            | Bumps versions in package.json + lockfile                    | Reports only; operator controls fixes |
| Rate                   | Configurable schedule (daily/weekly)                         | Runs on every PR                      |
| GitHub integration     | Native GitHub feature                                        | CI-native — same model as secret-scan |
| Free for private repos | Requires GitHub Advanced Security (paid for some plans)      | Free — npm is free                    |

**Decision:** `npm audit` in CI is simpler, cheaper, and sufficient for the immediate need. Dependabot can be evaluated as a future enhancement (SEC-009.3+) if automated PR-based remediation is desired.

### 5.4 Why not OSV-Scanner

| Factor           | OSV-Scanner                                    | npm audit       |
| ---------------- | ---------------------------------------------- | --------------- |
| Scope            | Multi-ecosystem (npm, pip, go, etc.)           | npm only        |
| Advisory source  | OSV database (aggregates multiple sources)     | npm advisory DB |
| Integration      | Requires installation (`go install` or binary) | Built-in        |
| Output           | JSON, SARIF, table                             | Table, JSON     |
| Lockfile support | Yes                                            | Yes             |

**Decision:** OSV-Scanner provides broader coverage but adds installation complexity and an external dependency. For a Node.js-only project, `npm audit` is sufficient. OSV-Scanner can be evaluated as a future enhancement.

## 6. Severity / BLOCK-WARN-INFO Policy

### 6.1 Threshold: `--audit-level=high`

| npm audit level | CI behavior     | Rationale                                       |
| --------------- | --------------- | ----------------------------------------------- |
| critical        | BLOCK           | Always block — known exploited or severe impact |
| high            | BLOCK           | Industry standard for CI gates                  |
| moderate        | INFO (no block) | informational; may include devDep-only issues   |
| low             | INFO (no block) | Rarely exploitable; noise in CI                 |
| info            | INFO (no block) | Purely informational                            |

### 6.2 Why `high` and not `moderate`

- `moderate` findings often include devDependency-only issues that do not affect production
- Blocking on `moderate` would create CI noise and slow development
- The current repo has 1 moderate (root: `@tailwindcss/postcss` via `postcss`) — blocking on it would require fixing postcss before any PR can merge
- `high` captures the findings that actually matter: SSRF, DoS, path traversal, information disclosure

### 6.3 Exit code behavior in CI

`npm audit --audit-level=high` returns:

- **Exit code 0** when no high or critical vulnerabilities are found → job passes
- **Exit code 1** when one or more high or critical vulnerabilities are found → job fails

This is the standard mechanism. No custom parsing, no `grep`, no `jq`. The exit code IS the signal.

### 6.4 Why not `--audit-level=critical` only

- `critical` only catches the most severe issues (e.g., remote code execution)
- `high` includes SSRF, path traversal, DoS, information disclosure — all real risks
- Industry standard (OWASP, Snyk, Socket.dev) uses `high` as the CI blocking threshold

## 7. CI Architecture

### 7.1 Job specification

```yaml
dependency-scan:
  name: dependency-scan
  runs-on: ubuntu-latest
  timeout-minutes: 10
  permissions:
    contents: read
  steps:
    - name: Checkout
      uses: actions/checkout@v4

    - name: Setup Node
      uses: actions/setup-node@v4
      with:
        node-version: ${{ env.NODE_VERSION }}
        cache: npm
        cache-dependency-path: |
          package-lock.json
          backend/package-lock.json

    - name: Install root dependencies
      run: npm ci

    - name: Install backend dependencies
      run: npm ci --prefix backend

    - name: Audit root dependencies
      run: npm audit --audit-level=high

    - name: Audit backend dependencies
      run: npm audit --prefix backend --audit-level=high
```

### 7.2 Key design decisions

| Decision               | Value                                                                            | Rationale                                                        |
| ---------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Job name               | `dependency-scan`                                                                | Stable; matches `secret-scan` naming convention                  |
| `timeout-minutes`      | 10                                                                               | Audit is fast; 10min covers `npm ci` install + audit             |
| `permissions`          | `contents: read`                                                                 | Same as all other jobs; minimum privilege                        |
| `actions/checkout`     | `@v4`                                                                            | Consistent with existing jobs (SEC-009.0 standard)               |
| `npm ci`               | Both root and backend                                                            | Required before audit — `npm audit` needs installed node_modules |
| Two audit steps        | `npm audit --audit-level=high` + `npm audit --prefix backend --audit-level=high` | Independent lockfiles; both must pass                            |
| No `--force`           | Never in CI                                                                      | Operator controls lockfile changes locally                       |
| No `continue-on-error` | Not used                                                                         | Failure blocks the PR — that is the point                        |

### 7.3 Why NOT `@v6` for checkout

The existing jobs in `ci.yml` are `secret-scan` plus the SEC-009.0 jobs (`security-tests`, `tests`, `backend-tests`, `typecheck`, `build`). `secret-scan` uses `actions/checkout@v6`. For consistency with the 009.0 job pattern, this design uses `checkout@v4` for `dependency-scan`. This is not a security issue — `@v4` is still supported and functional.

### 7.4 Relationship with other jobs

The `dependency-scan` job runs **in parallel** with all other jobs. It does NOT depend on `secret-scan`, `security-tests`, `tests`, `backend-tests`, `typecheck`, or `build`. Each job is a leaf job.

```
PR opened
├── secret-scan          (gitleaks)
├── dependency-scan      (npm audit) ← NEW
├── security-tests       (vitest security suite)
├── tests                (vitest root)
├── backend-tests        (vitest backend)
├── typecheck            (tsc --noEmit)
└── build                (next build + tsc)
```

### 7.5 Why a single job (not two)

Two separate jobs (`dependency-scan-root`, `dependency-scan-backend`) would:

- Double the GitHub Actions minutes consumed
- Require two status checks instead of one
- Add complexity without benefit (both are fast, both need Node setup)

A single job with two audit steps is simpler, cheaper, and produces one clear status check.

## 10. Exception / Remediation Policy

### 10.1 Vulnerability with fix available

**Policy:** Fix it. Run `npm audit fix` (safe) or update the specific package.

```powershell
# Safe fix (semver-compatible)
npm audit fix

# Backend
npm audit fix --prefix backend
```

### 10.2 Vulnerability with no fix available

**Policy:** Document the exception. Create a tracking issue. Set a review date.

If no upstream fix exists:

1. Document the advisory URL, affected package, and impact assessment
2. Create a GitHub issue tagged `security` with a 30-day review date
3. The CI gate will block PRs — this is intentional (forces attention)
4. If the vulnerability is truly not exploitable in this codebase, the operator must make an explicit, documented risk acceptance

**No silent bypasses.** No `|| true`. No `continue-on-error`. No modifying lockfiles in CI.

### 10.3 Vulnerability in transitive dependency

**Policy:** Fix the direct dependency that pulls in the transitive vulnerability.

`npm audit` output shows the dependency chain. The fix is always to update the direct dependency (or accept the risk if no fix exists).

### 10.4 Vulnerability in devDependency only

**Policy:** Same as production dependencies. Supply chain attacks target dev dependencies too (e.g., `shell-quote` via `concurrently`).

Do NOT exempt devDependencies from scanning.

### 10.5 Advisory with questionable exploitability

**Policy:** Document the assessment. Block anyway.

If the advisory seems non-exploitable but is rated high/critical:

1. The CI gate blocks — this is correct behavior
2. Document why the team believes it is not exploitable
3. Track it as a tech debt item
4. Re-evaluate when upstream provides a fix

### 10.6 Temporary exception (emergency)

If a vulnerability must be temporarily accepted (e.g., fix breaks critical functionality):

1. Create a GitHub issue with the advisory details
2. Assign to a team member with a 7-day deadline
3. Add a comment in the issue explaining the risk acceptance
4. **No code-level bypasses** — the CI gate remains active

---

## 1. Resumen ejecutivo

Hoy todos los emails salen por **Resend** desde el proceso HTTP de Express, casi siempre en modo **fire-and-forget** (`.catch` / promesas sin `await`). El outbox (`049`) ya emite `reservation.created.v1` en la misma transacción que el `INSERT` de la reserva, pero **nadie lo consume**.

El Email Worker puede basarse en infra existente (`email.service`, `getTicketData`, `ticket_email_sent_at`) **sin** Redis/BullMQ/Kafka. El hallazgo crítico es una **race** entre el outbox (commit del RPC) y el `UPDATE` posterior de `contact_email` / `send_ticket_email` en el service layer.

## 3. Auditoría profunda — `reservation.created` / ticket email

### 3.1 Flujo actual (después de WKR-004)

```
HTTP POST create reservation
  │
  ├─► RPC create_agency_reservation
  │     ├─ INSERT reservations (qr_code, ticket_code, …)
  │     │     └─ TRIGGER → outbox_events pending
  │     │                   payload: {reservation_id, trip_id, agency_id}
  │     ├─ INSERT reservation_passengers
  │     └─ UPDATE seats → reserved
  │
  ├─► await generateQRDataURL(qr)          ← síncrono, respuesta UI
  ├─► notificationService.createForAgency  ← fire-and-forget (in-app admin)
  ├─► UPDATE contact_email, send_ticket_email   ← DESPUÉS del commit RPC
  └─► if send && email:
        getTicketData → PNG → Resend → ticket_email_sent_at
        (fire-and-forget)
```

### 3.2 Componentes

| Pieza | Dónde | Notas |
|-------|-------|-------|
| QR textual | RPC `047` (`qr_code`) | Persistido; fuente de verdad |
| QR data URL | `reservation.service` + `getTicketData` | Regenerable; no está en outbox |
| Ticket PNG | `generateTicketPNG` en `email.service` | CPU; fallo PNG **no** bloquea el email HTML |
| Resend | `sendReservationConfirmationEmail` | Lanza si Resend falla |
| Notificación in-app | `notificationService` tipo `reservation_created` | Separada del email; no es efecto del outbox aún |
| Flags email | `031_add_reservation_ticket_email.sql` | `contact_email`, `send_ticket_email`, `ticket_email_sent_at` |

### 3.3 Fallos posibles

1. Resend down / rate limit → email perdido; `ticket_email_sent_at` queda `null`.
2. PNG falla → email sin adjunto (parcialmente OK).
3. Proceso API muere tras commit y antes del fire-and-forget → email perdido; **outbox sí tiene el evento**.
4. `getTicketData` falla → catch log `TICKET_EMAIL_FAILED`.
5. Preferencias: el email de ticket **no** pasa por `notificationDeliveryPolicy` (solo trip emails).

### 3.4 Inconsistencias posibles

| Escenario | Estado DB | Email | Outbox |
|-----------|-----------|-------|--------|
| Reserva OK, email OK | `ticket_email_sent_at` set | Enviado | `pending` (sin consumer) |
| Reserva OK, email falla | `ticket_email_sent_at` null | No | `pending` |
| Reserva OK, `send_ticket_email=false` | flags false | No | **Igual** `pending` (evento siempre) |
| Dual run futuro (HTTP + worker) | Ambiguo | **Duplicado** | — |

### 3.5 Duplicación posible

- Hoy: un solo path fire-and-forget → bajo riesgo de doble envío salvo reintento manual del cliente creando otra reserva.
- Con worker **sin** apagar el path HTTP: **doble email** casi seguro.
- Mitigación: idempotencia con `ticket_email_sent_at IS NULL` (update condicional ya existe) + feature flag para desactivar el path HTTP.

### 3.6 Race crítica (hallazgo principal)

Orden temporal:

1. Trigger outbox corre en el **commit del RPC** (flags aún default: `send_ticket_email=false`, `contact_email=null`).
2. El service **después** hace `UPDATE` de flags y dispara el email.

Si el worker consume entre (1) y (2), leerá “no enviar” y marcará el evento como no-op/completado **incorrectamente**.

**Opciones para WKR-005 (decisión pendiente):**

| Opción | Pros | Contras |
|--------|------|---------|
| A. Delay `available_at` (+2–5 s) en trigger o relay | Simple | Frágil bajo carga |
| B. Worker: si flags ausentes y evento reciente → requeue (`available_at` + backoff) | Robusto | Lógica de “aún no listo” |
| C. Mover `contact_email`/`send_ticket_email` al RPC | Elimina race | Cambia contrato RPC (fuera de WKR-005 mínimo) |
| D. Solo completar “skip” si `created_at` > N segundos y flags siguen false | Combina B | Heurística |

**Recomendación:** B (+ D) en WKR-005; C como mejora posterior.

## 4. Contrato conceptual — `ReservationCreatedHandler`

### Input

```ts
{
  event: ReservationCreatedEventV1; // parseado desde outbox row
  // data: { reservation_id, trip_id, agency_id }
}
```

El handler **no** recibe PII del outbox; relee por `reservation_id` (service_role).

### Output (resultado de negocio)

| Resultado | Significado | Outbox status |
|-----------|-------------|---------------|
| `sent` | Email enviado; `ticket_email_sent_at` seteado | `completed` |
| `skipped_no_email_requested` | `send_ticket_email=false` o sin `contact_email` (tras ventana de settle) | `completed` |
| `skipped_already_sent` | `ticket_email_sent_at` ya no null | `completed` |
| `retryable_failure` | Resend/timeout/DB transient / flags not settled | `pending` + `attempts++` + `available_at` backoff |
| `permanent_failure` | Reserva inexistente, payload inválido, versión desconocida | `failed` (+ DLQ futura) |

### Estados del outbox (ya en `049`)

`pending` → `processing` → `completed` | `failed`

### Errores

| Clase | Ejemplos | Acción |
|-------|----------|--------|
| Recuperables | Resend 429/5xx, timeout red, DB lock, flags no settled | Retry con backoff; max attempts |
| No recuperables | Reserva no encontrada, `event_version` desconocida, payload PII/ inválido | `failed`; no reintentar ciego |

## 5. Idempotencia

### Campos existentes

| Campo | Tabla | Uso |
|-------|-------|-----|
| `ticket_email_sent_at` | `reservations` | Update condicional `.is('ticket_email_sent_at', null)` — **idempotencia de entrega del ticket** |
| `send_ticket_email` | `reservations` | Intención del usuario |
| `contact_email` | `reservations` | Destinatario |
| `outbox_events.id` | outbox | Identidad del evento |
| `outbox_events.status/attempts` | outbox | Máquina de entrega del relay |

### ¿Hace falta event delivery tracking aparte?

| Enfoque | Suficiente para ticket email? |
|---------|-------------------------------|
| Solo `ticket_email_sent_at` | **Sí** para no reenviar el mismo ticket |
| Solo marcar outbox `completed` | No basta si hay otro consumidor (notif) |
| Tabla `(consumer, event_id)` | Recomendada cuando haya **varios** handlers del mismo evento |

**Estrategia recomendada (WKR-005):**

1. Relay reclama fila (`pending` → `processing`) con `FOR UPDATE SKIP LOCKED`.
2. Handler lee reserva:
   - si `ticket_email_sent_at` set → `skipped_already_sent` → `completed`
   - si no debe enviar (flags settled false) → `skipped` → `completed`
   - si debe enviar → Resend → set `ticket_email_sent_at` condicional → `completed`
3. Más adelante: tabla `outbox_consumer_receipts(consumer_name, event_id)` cuando NotificationWorker consuma el mismo evento.

## 6. Seguridad del payload `reservation.created.v1`

Confirmado en migración `049` + `backend/src/events/reservation-created.v1.ts`:

```json
{
  "reservation_id": "…",
  "trip_id": "…",
  "agency_id": "…"
}
```

- Sin documentos, teléfonos, emails, QR, nombres, pasajeros.
- Outbox: RLS deny-by-default, solo `service_role`, fuera de Realtime.
- El worker carga PII **solo en memoria** vía `getTicketData` para construir el email (igual que hoy).

ADR-001: `agency_id` del payload es **ownership comercial**; no autoriza boarding.

## 7. Arquitectura propuesta (sin tecnología nueva)

```
PostgreSQL outbox_events
        │
        ▼
 Outbox Relay (proceso Node, mismo repo)
   - poll status=pending AND available_at <= now()
   - claim → processing
   - dispatch by event_type + version
        │
        ▼
 ReservationCreatedHandler (Email)
   - parseReservationCreatedEventV1
   - load reservation (flags + getTicketData)
   - emailService.sendReservationConfirmationEmail
   - set ticket_email_sent_at
        │
        ▼
 completed | failed | requeue (available_at, attempts++)

 Max attempts exceeded → failed (DLQ lógica / inspección)
```

| Pieza | Notas |
|-------|-------|
| Relay | Loop en `nomadas-worker` (WKR-002); sin Redis |
| Handlers | Un handler por `type+version` |
| Retries | `attempts`, backoff en `available_at`, `error_message` |
| Dead letter | Primero `status=failed`; tabla `outbox_events_dead` opcional después |
| API | Feature flag: dejar de fire-and-forget cuando worker estable |

**No introducir:** Redis, BullMQ, Kafka, cambios al proveedor Resend.

## 8. Hallazgos

1. Outbox listo; email ticket sigue acoplado al HTTP.
2. Race `outbox` vs `UPDATE` de `contact_email`/`send_ticket_email`.
3. `ticket_email_sent_at` ya da idempotencia de envío.
4. PNG es best-effort; el email HTML es el camino crítico.
5. Notificación in-app es canal paralelo (no mover en WKR-005).
6. Otros 6 emails no tienen evento de outbox todavía.

## 9. Riesgos

| Riesgo | Severidad | Mitigación |
|--------|-----------|------------|
| Race flags post-RPC | Alta | Requeue si evento “fresco” y flags vacíos |
| Doble envío HTTP+worker | Alta | Flag + `ticket_email_sent_at` |
| Worker multi-réplica | Media | `SKIP LOCKED` + claim atómico |
| Crecimiento outbox | Media | RetentionWorker posterior |
| Email sin PNG | Baja | Comportamiento actual aceptable |

## 11. Recomendación para WKR-005 (implementación)

**Alcance mínimo viable:**

1. Proceso/loop **Outbox Relay** (Node, service_role) que reclama `reservation.created` v1.
2. **`ReservationCreatedHandler`**: settle flags → skip o `getTicketData` + `sendReservationConfirmationEmail` + `ticket_email_sent_at`.
3. Retries vía `attempts` / `available_at` / `error_message`.
4. Feature flag `EMAIL_VIA_OUTBOX=true` para desactivar el path fire-and-forget en `reservation.service`.
5. Tests: unit handler (skip/sent/already_sent/retry) + SQL/static de claim.
6. **No** migrar trip/auth emails en este ticket.
7. Documentar runbook de `failed` events.

**Fuera de WKR-005:** scheduler, reminders, BullMQ, cambiar Resend, NotificationWorker, mover flags al RPC (salvo que se elija explícitamente).

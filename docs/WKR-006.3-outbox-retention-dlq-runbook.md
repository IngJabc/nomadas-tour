## 1. Objetivo

El outbox ya procesa eventos de forma confiable (claim, retry, stuck recovery, logs, Sentry opcional). Falta la capa **operativa**:

| Necesidad | Sin política | Con este runbook |
|-----------|--------------|------------------|
| Eventos `completed` | La tabla crece sin bound | Retención + purga futura |
| Eventos `failed` | Sin procedimiento | DLQ lógica + investigación / reintento |
| Incidentes | Ad hoc en SQL | Pasos seguros y repetibles |

Esto cierra la infraestructura de workers **antes** de agregar más consumers (WKR-007+).

`public.outbox_events` (migración `049_outbox_events.sql`)

## 3. Política de retención

### `completed`

| Regla | Valor inicial |
|-------|----------------|
| Conservar | **30 días** desde `processed_at` (o `updated_at` si `processed_at` null) |
| Purgar | DELETE (o archive futuro) de filas elegibles |
| Criterio | `status = 'completed' AND processed_at < now() - interval '30 days'` |
| Quién | **WKR-009** ✅ — scheduler + RPC `purge_completed_outbox_events` (flag `OUTBOX_RETENTION_VIA_WORKER`); o SQL ops controlado (§5.5) |
| Frecuencia | Poll diario por defecto en el worker (24h); ajustable vía env |

**Por qué 30 días:** suficiente para soporte/debug post-reserva; payload sin PII reduce sensibilidad de retención larga.

### `failed`

| Regla | Valor inicial |
|-------|----------------|
| Auto-delete | **No** |
| Conservar | Indefinido hasta resolución ops o política futura |
| Motivo | Auditoría, root-cause, posible reintento manual |

Revisión periódica recomendada (ops): semanal `COUNT(*) WHERE status = 'failed'`.

### `processing`

No es retención: si queda stale → `recover_stuck_outbox_events` (WKR-006.1).  
No borrar filas `processing` a mano sin verificar que ningún worker las tiene.

### `pending`

No purgar. Son trabajo en cola (incl. delayed por backoff / settle).

## 4. Estrategia DLQ (lógica)

**DLQ inicial = filas con `status = 'failed'`.**  
No hay tabla `outbox_dlq` ni broker.

### Cuándo pasa a `failed`

1. Outcome permanente del handler (ej. contrato inválido, reserva inexistente).
2. `attempts >= OUTBOX_MAX_ATTEMPTS` tras requeues / errores temporales.
3. Sin handler registrado para `event_type` + `event_version`.

### Qué se conserva

- Identidad del evento (`id`, type, version, aggregate, tenant)
- `payload` mínimo (IDs)
- `attempts`, `error_message`, timestamps
- Logs correlacionados (`event_id`) y, si aplica, evento Sentry (fallos inesperados)

### Cómo investigar

1. Leer fila `failed` (SQL abajo).
2. Correlacionar logs worker: `outbox_failed`, `handler_error`, `event_id`.
3. Revisar agregado de dominio (ej. `reservations` por `aggregate_id`) **sin** copiar PII a tickets públicos.
4. Decidir: reintentar / ignorar / fix de código + reintento.

## 5. Operación manual

> Ejecutar en Supabase SQL Editor (o psql) con rol adecuado (`service_role` / admin).  
> Preferir transacciones y `LIMIT` en updates masivos.

### 5.1 Revisar eventos fallidos

```sql
-- Resumen
SELECT event_type, event_version, COUNT(*) AS n,
       MAX(updated_at) AS last_failure
FROM public.outbox_events
WHERE status = 'failed'
GROUP BY 1, 2
ORDER BY n DESC;

-- Detalle reciente
SELECT id, event_type, event_version, aggregate_type, aggregate_id,
       tenant_id, attempts, error_message, created_at, updated_at, processed_at
FROM public.outbox_events
WHERE status = 'failed'
ORDER BY updated_at DESC
LIMIT 50;

-- Un evento concreto
SELECT *
FROM public.outbox_events
WHERE id = '<event_uuid>';
```

Backlog / salud rápida:

```sql
SELECT status, COUNT(*) FROM public.outbox_events GROUP BY status;

SELECT COUNT(*) AS pending_ready
FROM public.outbox_events
WHERE status = 'pending' AND available_at <= NOW();

SELECT COUNT(*) AS stuck_processing
FROM public.outbox_events
WHERE status = 'processing'
  AND updated_at < NOW() - INTERVAL '5 minutes';
```

### 5.2 Reintentar un evento (`failed` → `pending`)

**Solo** si la causa raíz ya está resuelta (bug fix, Resend ok, datos corregidos).

```sql
BEGIN;

UPDATE public.outbox_events
SET
  status = 'pending',
  available_at = NOW(),
  error_message = left(
    COALESCE(error_message || '; ', '') || 'manual_requeue',
    2000
  ),
  processed_at = NULL,
  updated_at = NOW()
  -- Opcional: resetear attempts si el fallo era infra y se quiere presupuesto fresco
  -- , attempts = 0
WHERE id = '<event_uuid>'
  AND status = 'failed'
RETURNING id, status, attempts, available_at;

COMMIT;
```

Notas:

- Dejar `attempts` sin reset evita loops infinitos si el bug sigue.
- Resetear `attempts = 0` solo con causa clara y monitoreo.
- El worker debe estar corriendo (`npm run worker`).

### 5.3 Reintentar un lote (mismo `event_type`, con cuidado)

```sql
-- Dry-run
SELECT id, attempts, error_message, updated_at
FROM public.outbox_events
WHERE status = 'failed'
  AND event_type = 'reservation.created'
  AND updated_at > NOW() - INTERVAL '7 days'
ORDER BY updated_at
LIMIT 20;

-- Aplicar solo tras dry-run
UPDATE public.outbox_events
SET status = 'pending', available_at = NOW(),
    processed_at = NULL, updated_at = NOW(),
    error_message = left(COALESCE(error_message || '; ', '') || 'manual_requeue_batch', 2000)
WHERE id IN (
  SELECT id FROM public.outbox_events
  WHERE status = 'failed' AND event_type = 'reservation.created'
  ORDER BY updated_at
  LIMIT 20
);
```

### 5.4 Ignorar un evento

Cuándo:

- El efecto ya ocurrió fuera del worker (email enviado manualmente, `ticket_email_sent_at` set).
- Evento obsoleto (viaje cancelado, agregado borrado) y reintento sería incorrecto.
- Fallo de datos irrecuperable y se acepta no procesar.

Cómo (marcar como completed “ack” ops — no borrar `failed` sin registro):

```sql
UPDATE public.outbox_events
SET
  status = 'completed',
  processed_at = NOW(),
  updated_at = NOW(),
  error_message = left(
    COALESCE(error_message || '; ', '') || 'manual_ack_ignored',
    2000
  )
WHERE id = '<event_uuid>'
  AND status = 'failed'
RETURNING id, status, error_message;
```

Alternativa: dejar en `failed` y documentar en el ticket de incidente (preferible si se quiere auditoría visible en la DLQ).

### 5.5 Purga manual de `completed` antiguos (emergencia)

Solo si se necesita intervención manual adicional al job WKR-009:

```sql
-- Dry-run
SELECT COUNT(*) FROM public.outbox_events
WHERE status = 'completed'
  AND processed_at < NOW() - INTERVAL '30 days';

-- Purga acotada
DELETE FROM public.outbox_events
WHERE id IN (
  SELECT id FROM public.outbox_events
  WHERE status = 'completed'
    AND processed_at < NOW() - INTERVAL '30 days'
  ORDER BY processed_at
  LIMIT 1000
);
```

Repetir en lotes. **Nunca** incluir `failed` en esta purga.

## 6. Retention Worker (WKR-009) ✅

**Estado:** implementado y cerrado (2026-08-12). Ver [`WKR-009-outbox-retention-workers-audit.md`](WKR-009-outbox-retention-workers-audit.md).

| Responsabilidad | Detalle |
|-----------------|---------|
| Purgar `completed` | Automático ≥30d (`COALESCE(processed_at, updated_at)`); RPC `purge_completed_outbox_events` + scheduler Node |
| Flag | `OUTBOX_RETENTION_VIA_WORKER` (default `false` en código; activo en Render tras cutover) |

| **No** | Borrar `failed` sin política explícita posterior; no automation bridge; no timers API |

## 7. Observabilidad

### Logs (WKR-006.1)

| Evento | Uso ops |
|--------|---------|
| `outbox_failed` | Entrada a DLQ lógica |
| `outbox_requeued` | Retry / settle (no DLQ) |
| `outbox_recovery_completed` / alias recovered stuck | Stuck `processing` recuperados |
| `outbox_claimed` / `outbox_completed` | Flujo sano |

Correlacionar siempre por `event_id`.

### Métricas in-memory (heartbeat)

| Métrica | Señal |
|---------|--------|
| `events_failed_total` | Fallos en este proceso desde boot |
| `events_retried_total` | Requeues |
| Stock SQL `failed` | DLQ real persistida |

### Sentry (WKR-006.2)

- Errores **inesperados** (loop, recovery RPC, max_attempts por excepción, uncaught).
- **No** sustituye revisar la tabla `failed`.
- Requeues normales / skips / completed → no van a Sentry.

## 9. Riesgos

| Riesgo | Impacto | Mitigación |
|--------|---------|------------|
| Crecimiento de `completed` | Disco / queries más lentas | Política 30d + WKR-009 |
| `failed` acumulados | DLQ opaca | Review semanal + fix + requeue/ack |
| Errores permanentes | Emails/notifs perdidos | Alertar por COUNT failed; Sentry en casos inesperados |
| Reintentos “infinitos” | Mitigado por `max_attempts` | No resetear `attempts` en masa sin criterio |
| Requeue manual incorrecto | Doble efecto | Idempotencia de handlers (`ticket_email_sent_at`) + verificar dominio antes |
| Purga agresiva | Pérdida de forense | Dry-run; no tocar `failed` |

---

## 10. Decisiones tomadas

1. **PostgreSQL** sigue siendo el único almacén del outbox.  
2. **DLQ lógica** = `status = 'failed'` — sin tabla/broker nuevo.  
3. **Sin** Kafka, Redis, BullMQ, RabbitMQ, Event Sourcing.  
4. Retención de `completed`: **30 días**; purga automática **WKR-009** ✅.  
5. `failed`: **sin auto-delete** en esta fase.  
6. Este ticket es **runbook + política**; **sin cambios de código**.  
7. Stuck `processing` permanece responsabilidad de WKR-006.1 (051).

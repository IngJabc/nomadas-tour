### Migration 036 Warning (Non-Blocking Risk)

`036_rls_identity_from_public_users.sql` contains:

```sql
-- *** NO APLICAR — superseded by 039_rls_identity_from_public_users_v2.sql ***
```

**No SQL guard exists.** The file contains only DROP/CREATE POLICY statements. `supabase db reset` will execute it.

**Risk assessment:** On a fresh database, 036 creates policies using inline `EXISTS(public.users)` pattern. Migration 039 then drops and recreates all those same policies using `private.auth_app_role()` helpers. The sequence 036 then 039 should complete without errors. The 42P17 recursion warning in 036 header was a production concern, not a fresh-database concern.

**Recommendation:** Monitor during first CI run. If 036 causes issues, rename to `.ignore` or add SQL guard.

### Auth Helpers (Verified from Migration 039)

```sql
CREATE OR REPLACE FUNCTION private.auth_app_role()
RETURNS text LANGUAGE plpgsql STABLE SECURITY DEFINER
SET search_path = ''
AS $$
BEGIN
  RETURN (SELECT u.role FROM public.users AS u WHERE u.id = (SELECT auth.uid()) LIMIT 1);
END;
$$;

CREATE OR REPLACE FUNCTION private.auth_app_agency_id()
RETURNS uuid LANGUAGE plpgsql STABLE SECURITY DEFINER
SET search_path = ''
AS $$
BEGIN
  RETURN (SELECT u.agency_id FROM public.users AS u WHERE u.id = (SELECT auth.uid()) LIMIT 1);
END;
$$;
```

**GRANT chain:**

```sql
REVOKE ALL ON FUNCTION private.auth_app_role() FROM PUBLIC;
REVOKE ALL ON FUNCTION private.auth_app_agency_id() FROM PUBLIC;
GRANT EXECUTE ON FUNCTION private.auth_app_role() TO authenticated;
GRANT EXECUTE ON FUNCTION private.auth_app_agency_id() TO authenticated;
GRANT USAGE ON SCHEMA private TO authenticated;
GRANT USAGE ON SCHEMA private TO service_role;
```

### JWT Claim Format (Reconciled)

Two formats exist in the repo:

- **Migration 039 comments:** `SET LOCAL request.jwt.claim.sub = '<uuid>'` (legacy per-claim GUC)
- **SEC-009.3 design doc:** `SET LOCAL request.jwt.claims = '{"sub": "<uuid>", ...}'` (modern JSON GUC)

**Correct format for current Supabase CLI (v2.115.0):** `request.jwt.claims` (JSON format). Modern PostgREST reads `auth.uid()` from `current_setting('request.jwt.claims', true)::jsonb->>'sub'`.

**NOT TESTED** — Docker required for real DB execution.

```sql
SET LOCAL role authenticated;

SELECT count(*) FROM public.reservations;  -- expect 0 (B's reservation not visible)

-- Own-data test:
-- Create reservation in Agency A
SELECT count(*) FROM public.reservations;  -- expect 1 (A's reservation visible)
```

**Expected mechanism:** RLS policies on `reservations` use `private.auth_app_agency_id()` to compare against `reservations.agency_id`. Agency A user sees only their own rows.

## 8. Service Role Boundary

**NOT TESTED** — understood from code analysis.

`service_role` bypasses all RLS policies. When using `supabaseAdmin` (service-role client):

- `SELECT * FROM reservations WHERE agency_id = B` returns all rows regardless of tenant
- RLS is completely bypassed
- This is why `service_role` cannot be used as the actor for isolation tests

The correct test actor is `authenticated` role with JWT claims, which is subject to RLS enforcement.

## 15. Recommendation

**Can SEC-009.3 full implementation proceed?**

```
CONDITIONAL YES
```

**Rationale:**

The spike was blocked on LOCAL Docker, not on CI Docker. All static evidence points to CI feasibility:

- Docker runs natively on `ubuntu-latest` without elevation
- Supabase CLI v2.115.0 is reproducible
- 71 migrations are statically sound (no obvious blockers)
- Auth helper mechanism is well-understood from code analysis
- JWT claim format is reconciled (`request.jwt.claims` for modern, `request.jwt.claim.sub` as legacy fallback)
- Node dependencies available (`@supabase/supabase-js`, `pg`, `vitest`)
- Estimated CI runtime (3-5 min) well within 15-min budget

**The remaining unknowns (runtime validation) should be resolved during the FIRST CI run of the tenant isolation job, not before implementation begins.** This is the standard approach for CI infrastructure validation.

### Conditions

1. **First CI run IS the runtime spike.** The initial `tenant-isolation` job should be implemented as a non-blocking informational job (not Required Status Check) until it proves stable.
2. **Migration 036 must be monitored.** If it errors, rename to `.ignore`.
3. **JWT claim format should be validated in first test.** Fallback to legacy format if needed.
4. **Local development requires Docker Desktop running.** Document this clearly.

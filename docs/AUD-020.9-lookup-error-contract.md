# AUD-020.9 — Lookup error contract

## Causa encontrada

El lookup exacto (`ticket_code` / `qr_code`) encontraba la reserva, pero `buildBoardingLookupDTO` la denegaba por reglas operativas (p. ej. `TRIP_NOT_DEPARTED`). El servicio devolvía `[]` y el scanner trataba cualquier array vacío como “credencial inexistente”.

Evidencia típica: `boarding_attempts.outcome=denied` + `failure_code=TRIP_NOT_DEPARTED` mientras la UI mostraba “No se encontró una reserva…”.

## Comportamiento anterior

| Situación | Backend | Frontend |
|-----------|---------|----------|
| Credencial inexistente | `[]` | “No se encontró…” |
| Reserva encontrada, no autorizada | `[]` | Mismo mensaje (incorrecto) |
| Reserva permitida | `[dto]` | Mostraba resultado |

No había forma de distinguir *not found* vs *found but denied*.

## Nuevo contrato

Sin arrays. Un solo resultado opcional:

```ts
export type BoardingLookupFailureCode =
  | 'EMPTY_INPUT'
  | 'CREDENTIAL_NOT_FOUND'
  | 'AGENCY_NOT_ASSIGNED'
  | 'TRIP_NOT_DEPARTED'
  | 'TRIP_INVALID'
  | 'TRIP_NOT_FOUND'
  | 'RESERVATION_CANCELLED';

export interface BoardingLookupResponse {
  found: boolean;
  allowed: boolean;
  failure_code: BoardingLookupFailureCode | null;
  result: BoardingLookupDTO | null;
}
```

La lógica de autorización (`trip_agencies`, estado de viaje, cancelación, etc.) **no cambia**. Solo cambia la forma de la respuesta.

## Invariantes

Deben cumplirse siempre:

1. `allowed === true` ⇒ `found === true`
2. `allowed === true` ⇒ `failure_code === null` y `result !== null`
3. `allowed === false` ⇒ `failure_code !== null` y `result === null`
4. Nunca `allowed === true` con `found === false`
5. Respuestas bloqueadas no incluyen DTO ni PII (QR, documentos, teléfonos, booker)

## Ejemplos

### Input vacío

```json
{
  "found": false,
  "allowed": false,
  "failure_code": "EMPTY_INPUT",
  "result": null
}
```

### Credencial inexistente

```json
{
  "found": false,
  "allowed": false,
  "failure_code": "CREDENTIAL_NOT_FOUND",
  "result": null
}
```

### Encontrada pero bloqueada (viaje no salió)

```json
{
  "found": true,
  "allowed": false,
  "failure_code": "TRIP_NOT_DEPARTED",
  "result": null
}
```

### Permitida

```json
{
  "found": true,
  "allowed": true,
  "failure_code": null,
  "result": { /* BoardingLookupDTO mínimo existente */ }
}
```

## Frontend

- `agencyApi.lookupPassengerByQR` → `Promise<BoardingLookupResponse>`
- `getLookupFailureOperatorMessage(failure_code)` mapea códigos a copy de operador
- Scanner: si `!response.allowed` → mensaje de dominio + limpia estado; si permitido → `setScanResult(response.result)`
- Nunca se muestran `err.message`, SQL, PostgREST ni stacks

## Fuera de alcance (sin cambios)

- ADR-001
- `boarding_toggle` / migraciones / RLS
- reglas cross-agency / autorización operacional
- DTO mínimo permitido
- esquema de `boarding_attempts` (sigue escribiéndose)

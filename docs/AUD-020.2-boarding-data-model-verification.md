## 1. Resumen ejecutivo

El modelo actual soporta la remediación AUD-020.1 sin reconstruir las entidades
principales:

- el QR completo vive en `reservations.qr_code`;
- la reserva tiene una identidad UUID estable;
- cada pasajero está relacionado con una reserva y un puesto;
- `reservation_passengers.boarded` y `boarded_at` son la fuente de verdad del
  embarque;
- `boarding_logs` ya relaciona reserva, actor, agencia operadora y, para el
  flujo vigente, pasajero;
- `seats` pertenece al viaje y no admite `boarded` como estado persistido.

`ticket_code` no existe como columna. Sin embargo, el código corto ya existe
conceptualmente en la UI: varias superficies muestran los primeros ocho
caracteres del UUID de la reserva. El QR se genera con ese mismo UUID, sin
guiones, como sufijo de 32 caracteres. Por tanto, las reservas existentes
pueden recibir un `ticket_code` estable a partir de `reservations.id`.

La conversión no debe asumir que ocho caracteres hexadecimales son únicos.
Representan 32 bits; se necesita precheck de colisiones, constraint `UNIQUE` y
una estrategia de resolución/generación para altas futuras.

`trip_id` y `reservation_agency_id` pueden añadirse a `boarding_logs` con
backfill determinista mediante `reservations`. En cambio,
`state_before/state_after` no pueden reconstruirse con fidelidad para todos los
logs históricos: los flujos legacy podían registrar eventos agregados, omitir
el pasajero y crear eventos duplicados.

La eliminación de las tres rutas legacy tiene cero consumidores internos
activos encontrados. Continúa siendo necesario revisar access logs externos
antes de tratarla como un cambio sin consumidores.

### Resultado

**El modelo está preparado para AUD-020.1 con migraciones aditivas y
backfills controlados.** Las observaciones bloquean un despliegue ciego, no el
diseño:

1. validar datos vivos de `boarding_logs` y `seats`;
2. resolver colisiones de códigos cortos;
3. conservar como `NULL` los estados históricos no demostrables;
4. decidir por separado si Realtime cross-agency requiere ampliar RLS.

## 3. QR y ticket_code

### 3.1 Generación actual

La fuente autoritativa es la RPC
`create_agency_reservation` en
`supabase/migrations/014_agency_reservation_function.sql`.

Proceso:

1. genera `v_reservation_id := gen_random_uuid()`;
2. obtiene `routes.destination`;
3. elimina guiones del mismo UUID;
4. convierte destino y UUID a mayúsculas;
5. persiste el resultado en `reservations.qr_code`.

Formato:

```text
NT-{DESTINATION_UPPER}-{RESERVATION_UUID_WITHOUT_DASHES_UPPER}
```

Ejemplo:

```text
NT-LA OLLA-6BBD52E983AB495493EAEE20466C18A2
```

Separación conceptual:

```text
prefijo:
NT-LA OLLA-

serial corto:
6BBD52E9

entropía restante:
83AB495493EAEE20466C18A2
```

El segmento completo tiene 32 caracteres hexadecimales y corresponde al UUID
de la reserva sin guiones.

### 3.2 Estabilidad

El serial es estable:

- se deriva del `reservations.id` generado al crear la reserva;
- se persiste dentro de `qr_code`;
- no existe un flujo que regenere `reservations.id` o `qr_code`;
- tickets y emails ya muestran `reservation_id.slice(0, 8)`.

El código corto ya existe conceptualmente, pero no como dato normalizado.
Actualmente distintas superficies lo calculan de dos formas:

- primeros ocho caracteres de `reservation_id`;
- primeros ocho caracteres del último segmento de `qr_code`.

La primera forma es más segura: un destino puede contener guiones, por lo que
`qr_code.split('-').pop()` no debe ser la fuente del backfill.

### 3.3 Colisiones

Ocho caracteres hexadecimales ofrecen:

```text
16^8 = 2^32 = 4,294,967,296 combinaciones
```

El código es suficiente como identificador operacional si se persiste con
unicidad y manejo de colisiones, pero no puede asumirse único por derivación.
Por el efecto cumpleaños, el riesgo acumulado crece con el volumen:

| Reservas aproximadas | Probabilidad aproximada de al menos una colisión |
|----------------------|---------------------------------------------------|
| 1.000 | 0,012 % |
| 10.000 | 1,16 % |
| 50.000 | 25 % |
| 77.000 | 50 % |

Conclusión:

- derivar el candidato inicial es seguro;
- imponerlo como único sin precheck no es seguro;
- debe existir constraint `UNIQUE`;
- la creación futura debe regenerar o resolver el código ante colisión;
- el lookup debe usar igualdad exacta y rate limiting.

### 3.4 Reservas existentes y futuras

Reservas existentes:

1. agregar `ticket_code` nullable;
2. proponer `UPPER(LEFT(REPLACE(id::text, '-', ''), 8))`;
3. detectar duplicados antes del constraint;
4. asignar códigos alternativos únicos a colisiones;
5. validar formato;
6. agregar `UNIQUE`;
7. convertir a `NOT NULL`.

Reservas futuras:

- no es necesario regenerar el QR completo;
- `qr_code` puede conservar el formato actual;
- `ticket_code` debe persistirse en la misma transacción de creación;
- la RPC debe retornar ambos identificadores;
- la generación debe manejar `unique_violation` de forma acotada.

La extracción desde `reservations.id` también permite tratar QR no canónicos
sin intentar parsear destino o prefijo.

## 4. Compatibilidad de migración

### 4.1 Preflight obligatorio en DB viva

Antes de crear migraciones de AUD-020.1 deben ejecutarse consultas read-only
equivalentes a:

```sql
-- Volumen y período de logs
SELECT
  count(*) AS total,
  min(created_at) AS first_log,
  max(created_at) AS last_log
FROM public.boarding_logs;

-- Calidad de auditoría
SELECT
  action,
  count(*) AS total,
  count(*) FILTER (WHERE scanned_by_agency_id IS NULL) AS missing_operator_agency,
  count(*) FILTER (WHERE reservation_passenger_id IS NULL) AS missing_passenger,
  count(*) FILTER (WHERE jsonb_typeof(seat_ids) <> 'array') AS invalid_seat_ids
FROM public.boarding_logs
GROUP BY action;

-- Pasajero del log que no pertenece a la reserva indicada
SELECT count(*) AS mismatched_passenger
FROM public.boarding_logs bl
JOIN public.reservation_passengers rp
  ON rp.id = bl.reservation_passenger_id
WHERE rp.reservation_id <> bl.reservation_id;

-- Distribución actual de puestos
SELECT status, count(*)
FROM public.seats
GROUP BY status
ORDER BY status;

-- Clasificación de blocked
SELECT
  count(*) FILTER (
    WHERE rp.id IS NOT NULL AND rp.status = 'active' AND rp.boarded
  ) AS blocked_with_boarded_passenger,
  count(*) FILTER (
    WHERE rp.id IS NOT NULL AND rp.status = 'active' AND NOT rp.boarded
  ) AS blocked_with_unboarded_passenger,
  count(*) FILTER (WHERE rp.id IS NULL) AS blocked_without_passenger
FROM public.seats s
LEFT JOIN public.reservation_passengers rp ON rp.seat_id = s.id
WHERE s.status = 'blocked';

-- Colisiones del candidato ticket_code
WITH candidates AS (
  SELECT
    id,
    upper(left(replace(id::text, '-', ''), 8)) AS ticket_code
  FROM public.reservations
)
SELECT ticket_code, count(*) AS total, array_agg(id) AS reservation_ids
FROM candidates
GROUP BY ticket_code
HAVING count(*) > 1;

-- QR no canónicos respecto al UUID persistido
SELECT id, qr_code
FROM public.reservations
WHERE upper(right(qr_code, 32)) <>
      upper(replace(id::text, '-', ''));
```

No se debe ejecutar un cleanup ni convertir columnas a NOT NULL hasta validar
estos resultados.

### 4.2 Backfill de `boarding_logs`

#### Seguro y determinista

`trip_id`:

```text
boarding_logs.reservation_id
        → reservations.id
        → reservations.trip_id
```

`reservation_agency_id`:

```text
boarding_logs.reservation_id
        → reservations.id
        → reservations.agency_id
```

Ambos valores pueden poblarse mediante join. `reservation_id`, `trip_id` y
`agency_id` son NOT NULL; el FK con ON DELETE CASCADE evita conservar logs de
reservas eliminadas.

#### No reconstruible con fidelidad

`state_before` y `state_after` no están presentes en registros históricos.

No basta con inferir:

```text
board   → false / true
unboard → true / false
```

porque el flujo actual no es idempotente y puede haber creado logs repetidos
sin transición real. Además:

- logs legacy pueden agrupar varios puestos;
- `reservation_passenger_id` puede ser NULL;
- `correction` no determina una transición booleana;
- el estado actual del pasajero no demuestra el estado en la fecha del log.

Recomendación:

- crear `state_before/state_after` como nullable;
- escribirlos obligatoriamente para eventos nuevos;
- mantener NULL en históricos no demostrables;
- si se decide inferir algún subconjunto, etiquetarlo explícitamente como
  inferido y no usarlo como evidencia autoritativa.

### 4.3 Limpieza de `seats.status = 'blocked'`

No se recomienda:

- eliminar `blocked` de la constraint;
- convertir todos los `blocked` a `reserved`;
- dejar indefinidamente como bloqueados los casos demostrados como artefactos
  legacy.

Decisión condicional:

| Caso vivo | Acción recomendada |
|-----------|--------------------|
| `blocked` + pasajero activo y abordado | Candidato seguro a `reserved` |
| `blocked` + pasajero activo no abordado | Investigar antes de modificar |
| `blocked` sin pasajero activo | Investigar reserva, viaje y uso operacional |
| Cero filas `blocked` | No crear cleanup de datos |

Por tanto, solo hace falta una migración de limpieza si el preflight encuentra
filas atribuibles al boarding legacy. Debe ser específica, verificable y
conservar cualquier bloqueo operacional legítimo.

### 4.4 Eliminación del flujo legacy

Rutas a retirar:

```text
POST /api/agency/reservations/board
POST /api/agency/scanner/lookup
POST /api/agency/scanner/board
```

Cadena interna encontrada:

| Ruta | Controller | Service | Consumidor runtime |
|------|------------|---------|--------------------|
| `/reservations/board` | `boardPassenger` | `boardPassenger` | Ninguno |
| `/scanner/lookup` | `lookupReservation` | `lookupReservationByQR` | Ninguno |
| `/scanner/board` | `boardPassengers` | `boardPassengers` | Ninguno |

`lib/api.ts` define `agencyApi.boardPassenger`, pero no existe ninguna llamada
desde páginas, hooks o componentes. No existen clientes frontend para las dos
rutas `/scanner/*`.

Búsqueda realizada sobre:

- `app/`, `components/`, `hooks/`, `lib/`;
- backend routes, controllers y services;
- archivos de tests;
- scripts y configuración;
- documentación.

Resultado interno:

```text
0 consumidores frontend
0 llamadas backend indirectas
0 tests dependientes
0 scripts o configuraciones dependientes
```

Referencias restantes:

- wiring de las propias rutas/controllers/services;
- definición no usada en `lib/api.ts`;
- comentarios de migraciones históricas;
- AUD-020, AUD-020.1 y documentación de historial.

Estas referencias documentales no son dependencias runtime. El repositorio no
puede demostrar que no existan integraciones HTTP externas; antes del retiro se
deben revisar access logs de producción.

## 5. Riesgos encontrados

| Riesgo | Severidad | Consecuencia | Mitigación |
|--------|-----------|-------------|------------|
| Colisión de código corto de 32 bits | Media | Backfill o lookup ambiguo | Precheck, UNIQUE y retry |
| Parsear código desde `qr_code.split('-')` | Media | Destinos con guiones producen derivación frágil | Derivar desde `reservations.id` |
| Backfill ficticio de estados históricos | Alta para auditoría | Historial presenta transiciones no demostrables | NULL para datos no verificables |
| Filas `blocked` de origen desconocido | Media | Cleanup puede liberar bloqueos válidos | Clasificar datos vivos antes de migrar |
| Logs legacy sin pasajero/agencia operadora | Media | Auditoría histórica incompleta | Conservar NULL; exigir campos en eventos nuevos |
| Consumidores HTTP externos no inventariados | Media | Breaking change al retirar rutas | Revisar access logs y comunicar |
| RLS comercial no entrega Realtime cross-agency | Media | Agencia operadora no recibe eventos ajenos por JWT | Decisión explícita de policy o refetch API |
| INSERT cliente en `boarding_logs` depende de grants vivos | Media | Superficie de escritura innecesaria | Auditar grants y revocar si backend es único writer |
| QR/código exacto aún enumerable por fuerza bruta | Baja-Media | Intentos automatizados sobre 32 bits | Rate limiting, attempts y monitoreo |

### Limitaciones de evidencia

No fueron verificables sin acceso read-only a la instancia:

- cantidad de reservas, pasajeros y logs;
- número de puestos `blocked`;
- grants efectivos de producción;
- existencia de QR no canónicos;
- colisiones reales del candidato `ticket_code`;
- duplicados semánticos en logs;
- consumidores externos observables en access logs.

Estas limitaciones deben cerrarse como gate de P0, no durante la migración.

## 6. Recomendación para implementación AUD-020.1

### Modelo de reservas

Proceder con `reservations.ticket_code` como columna persistida y única.
Usar los primeros ocho caracteres hexadecimales del UUID solo como candidato de
backfill, no como garantía matemática de unicidad.

No regenerar QR existentes ni futuros por esta remediación. Mantener:

```text
qr_code    → credencial completa exacta
ticket_code → identificador corto exacto
```

### Modelo transaccional

El modelo permite implementar `boarding_toggle()`:

- lock de reserva y pasajero;
- validación de viaje y `trip_agencies`;
- actualización de `boarded`/`boarded_at`;
- recálculo de reserva;
- log transaccional.

No se necesitan nuevas relaciones para encontrar viaje, agencia propietaria o
puesto.

### Auditoría

Agregar `trip_id` y `reservation_agency_id` con backfill determinista.
Agregar `state_before/state_after` nullable y exigirlos para filas nuevas.
No fabricar estados históricos.

Crear `boarding_attempts` como tabla separada solo después de definir:

- retención;
- grants;
- hashing;
- outcomes;
- comportamiento ante fallos de telemetría.

### Asientos

Mantener la constraint actual, incluido `blocked`, porque puede representar
bloqueo operacional. Eliminar únicamente el write legacy que usa `blocked`
como sinónimo de boarding.

Ejecutar limpieza de datos solo si el preflight demuestra artefactos legacy.
El visual `boarded` debe continuar derivándose de
`reservation_passengers.boarded`.

### RLS

Si `service_role` continúa siendo la única vía de mutación:

- no hace falta ampliar RLS de `reservation_passengers` para ejecutar
  boarding;
- no hace falta permitir RPC a `authenticated`;
- sí deben restringirse grants de la RPC y de tablas de auditoría;
- debe revisarse si `bl_agency_insert` sigue siendo necesario.

RLS adicional basada en `trip_agencies` solo es necesaria si se requiere:

- Realtime cross-agency para la agencia operadora;
- lectura directa mediante JWT;
- integraciones futuras sin backend service role.

No ampliar policies por anticipación. Si se decide habilitar Realtime
cross-agency, crear policies de lectura mínimas y tests específicas.

### Secuencia recomendada

1. Ejecutar preflight de datos y grants en producción/staging.
2. Resolver colisiones y clasificar `blocked`.
3. Agregar tests de caracterización.
4. Retirar consumidores y rutas legacy.
5. Crear migraciones aditivas.
6. Desplegar RPC y grants antes del backend consumidor.
7. Activar lookup exacto.
8. Ejecutar tests concurrentes y smoke test cross-agency.
9. Actualizar documentación con resultados reales.

## 7. Conclusión

El modelo actual es compatible con AUD-020.1.

No se requiere reemplazar `reservations`, `reservation_passengers`, `seats` ni
`boarding_logs`. La remediación puede realizarse con:

- una columna persistida `ticket_code`;
- una RPC transaccional;
- columnas de auditoría aditivas;
- una tabla separada de intentos;
- retiro del código legacy;
- cleanup condicional de datos.

Respuestas finales:

| Pregunta | Respuesta |
|----------|-----------|
| ¿Existe `ticket_code`? | No |
| ¿Existe un serial reutilizable? | Sí, el UUID de reserva usado en el QR |
| ¿Es estable? | Sí |
| ¿Puede colisionar el prefijo de 8 caracteres? | Sí |
| ¿Se puede poblar para reservas existentes? | Sí, con precheck y resolución de colisiones |
| ¿Hay que regenerar QR futuros? | No |
| ¿`trip_id` y `reservation_agency_id` admiten backfill? | Sí, de forma determinista |
| ¿Estados before/after admiten backfill fiable? | No para todo el histórico |
| ¿Hay que limpiar `blocked`? | Solo si datos vivos confirman artefactos legacy |
| ¿Hay consumidores internos legacy? | No se encontraron |
| ¿La mutación requiere ampliar RLS? | No mientras use exclusivamente service role |

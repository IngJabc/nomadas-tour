## 1. Objetivo

Sentry entra **ahora** porque WKR-006.1 ya dejó la base operativa del worker:

- logs JSON estructurados
- correlación (`event_id`, `aggregate_id`, `tenant_id`, `handler`, `worker_name`)
- métricas in-memory + heartbeat
- recovery de `processing` stuck

Antes de eso, Sentry habría llegado sin contexto útil y con alto riesgo de ruido/PII.

**Sentry complementa** logs, métricas y heartbeat; **no los reemplaza**.  
Este ticket solo documenta la estrategia. **No instala SDK ni cambia código.**

Separación: Sentry = observabilidad de errores en runtime.  
**SEC-009** (Strix/SAST/scanners) = seguridad continua — ticket distinto.

## 3. Problemas que resuelve Sentry

- Errores de producción agrupados (API + worker)
- Stack traces y breadcrumbs
- Agrupación automática por fingerprint
- Alertas (email / integraciones según plan)
- Contexto del fallo vía tags (handler, event_id, tenant)
- Historial de regresiones entre releases

---

## 4. Problemas que NO resuelve

Sentry **no** reemplaza:

| Pieza | Sigue siendo fuente de verdad |
|-------|-------------------------------|
| Logs JSON stdout | Operación día a día, heartbeat, audit operativo |
| Métricas in-memory / futuras Prometheus | Throughput, backlog, retries |
| Dashboards de negocio | Producto / ops internos |
| Health checks | Liveness del proceso / SQL gauges |
| Retries / outbox / DLQ | Confiabilidad de eventos (WKR-006.3) |

## 5. Arquitectura propuesta

```text
┌─────────────┐     ┌──────────────────┐
│ Express API │     │ nomadas-worker   │
└──────┬──────┘     └────────┬─────────┘
       │                     │
       ▼                     ▼
┌──────────────────────────────────────┐
│ Structured Logs (stdout JSON)        │  ← permanece
│ Metrics (in-memory → heartbeat)      │  ← permanece
│ Heartbeat / recovery / retry         │  ← permanece
└──────────────────┬───────────────────┘
                   │ exceptions + tags
                   ▼
            ┌─────────────┐
            │   Sentry    │  ← WKR-006.2 (próximo)
            │ (errors)    │
            └─────────────┘
```

Ninguna pieza existente se elimina. Sentry es un **sink adicional** para excepciones y fallos permanentes seleccionados.

---

## 6. Integración Backend (propuesta WKR-006.2)

| Área | Enfoque |
|------|---------|
| Express | Init `@sentry/node` temprano; request handlers / error middleware |
| Unhandled exceptions | Capture + rethrow/exit según política del proceso API |
| Unhandled rejections | Capture; no silenciar |
| Errores inesperados | `errorHandler` → `captureException` si 5xx / no operacionales |
| RPC / Supabase failures | Capturar solo si no son errores de dominio esperados (4xx de negocio) |
| Background fire-and-forget | Si quedan paths HTTP async (email legacy), capturar rechazos |

**No** reportar cada `ValidationError` / `Forbidden` como evento Sentry (ruido).

---

## 7. Integración Worker (propuesta WKR-006.2)

| Área | Enfoque |
|------|---------|
| Lifecycle | Init al boot (`worker_started`); flush en shutdown |
| Relay loop | Capturar errores de claim/DB en `outbox_relay_loop_error` |
| Handlers | `captureException` en excepciones; tags desde `correlationFromRow` |
| Retry / settle | **No** enviar `flags_not_settled` / requeues normales a Sentry |
| Failed permanente / max attempts | Opcional: un evento con tags (rate-limited) |
| Shutdown | Flush Sentry antes de `exit` |
| Recover scheduler | Errores del RPC → capture; `recovered_count > 0` solo log |

Puntos ya listos en código (sin SDK): `worker_uncaught_exception`, `worker_unhandled_rejection`, `worker_fatal`, campos de correlación en logs.

## 8. Tags estándar (convención oficial)

| Tag / extra | Origen | Obligatorio |
|-------------|--------|-------------|
| `service` | `api` \| `worker` | Sí |
| `worker_name` | `nomadas-outbox-relay` | Worker |
| `handler` | `reservation.created:1` | Cuando hay evento |
| `event_type` | outbox | Cuando hay evento |
| `event_version` | outbox | Cuando hay evento |
| `aggregate_type` / `aggregate_id` | outbox | Cuando hay evento |
| `tenant_id` / `agency_id` | outbox / auth | Cuando exista |
| `event_id` | `outbox_events.id` | Cuando hay evento |
| `attempts` | outbox | Cuando hay evento |
| `status` | outcome | Cuando aplique |
| `environment` | `development` / `staging` / `production` | Sí |
| `release` | versión app/worker | Sí (si disponible) |
| `correlation_id` | futuro (HTTP→outbox) | No aún |

**Nunca** adjuntar payload completo del evento ni body de requests con PII.

---

## 9. Manejo de PII

**Nunca enviar a Sentry:**

- emails / `contact_email`
- documentos de identidad
- teléfonos
- nombres de pasajeros / booker
- QR / `ticket_code`
- payloads JSON completos de outbox o requests

**Sí permitido:** UUIDs (`event_id`, `aggregate_id`, `agency_id`, `trip_id`), tipos de evento, reasons no sensibles, mensajes de error técnicos scrubbed.

Implementación futura: `beforeSend` + denylist alineada al scrub del logger WKR-006.1.

## 10. Entornos

| Entorno | Sentry | Notas |
|---------|--------|-------|
| `development` (local) | **Off por defecto** | `SENTRY_DSN` vacío = no-op |
| `staging` | On (DSN staging) | Validar ruido antes de prod |
| `production` | On (DSN prod) | Sample rate conservador al inicio |

Misma org Sentry; projects o environments separados (`api` / `worker`).  
No activar reportes externos en máquinas de desarrollo sin DSN explícito.

## 11. Plan gratuito (Developer)

Referencia orientativa ([Sentry Pricing](https://docs.sentry.io/pricing/) — verificar al implementar; los cupos cambian):

| Ítem | Orden de magnitud Free (Developer) |
|------|-------------------------------------|
| Precio | $0 |
| Usuarios | 1 |
| Errors / mes | ~5 000 |
| Spans / mes | cupo incluido (tracing); **no usaremos Performance en WKR-006.2** |
| Session Replay | cupo bajo; **no integrar** en WKR-006.2 |
| Alertas | email básico |

**Por qué alcanza hoy**

- Un solo worker + API B2B, volumen de errores bajo si filtramos settle/4xx.
- Sin Performance ni Replay → casi solo error events.
- 5k errors/mes sobra si no se reporta cada requeue.

**Revisar al crecer**

- Más workers / tenants → más superficie de fallo
- Necesidad de varios usuarios / Slack / SSO → plan Team
- Activar tracing/replay → cupos y costo distintos  
**No se elige plan comercial en este ticket.**

## 13. Riesgos

| Riesgo | Mitigación |
|--------|------------|
| Costo / cuota Free | Filtrar ruido; sin spans/replay al inicio; monitorear usage |
| Ruido (settle requeues) | Never capture `flags_not_settled` / requeues normales |
| Duplicación (log + Sentry + exit) | Un capture por fallo; flush ordenado en shutdown |
| PII | `beforeSend` + convención tags-only |
| Over-reporting | No capturar 4xx de dominio; sample rate si hace falta |

---

## 14. Decisiones tomadas

1. No reemplazar logs JSON ni métricas in-memory.  
2. No capturar PII ni payloads.  
3. **No** integrar frontend en WKR-006.2.  
4. **No** Performance Monitoring en WKR-006.2.  
5. **No** Session Replay en WKR-006.2.  
6. Local off por defecto (`SENTRY_DSN` vacío).  
7. Sentry ≠ SEC-009.  
8. Este ticket es docs-only; wiring = WKR-006.2.

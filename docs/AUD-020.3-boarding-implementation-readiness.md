## 2. Decisiones cerradas

Las siguientes decisiones son definitivas y no deben reabrirse durante la
implementación:

1. `reservation.agency_id` sigue siendo ownership comercial.
2. `trip_agencies` autoriza boarding operacional.
3. `lookupPassengerByQR` + `toggleBoarding` será el único flujo.
4. Los endpoints legacy se eliminan:
   - `POST /agency/reservations/board`
   - `POST /agency/scanner/lookup`
   - `POST /agency/scanner/board`
5. Boarding pertenece a `reservation_passengers`, no a `seats`.
6. `seats.status` no tendrá estado persistido `boarded`.
7. La búsqueda manual será:
   - `ticket_code` exacto de 8 caracteres hexadecimales;
   - `qr_code` completo exacto.
8. No existirán búsquedas parciales con `ILIKE`.
9. El DTO de boarding será mínimo; no reutilizará DTOs administrativos.
10. `boarding_logs` representa transiciones reales (`changed=true`).
11. `boarding_attempts` representa intentos operacionales.
12. La RPC `boarding_toggle` será la frontera transaccional.
13. ADR-001 no se modifica.

## 6. Riesgos de implementación

| Riesgo | Control |
|--------|---------|
| `SECURITY DEFINER` mal configurado | Grants mínimos; `search_path` fijo; schemas calificados; validación interna de `trip_agencies` |
| Migración DB antes/después del backend | Publicar DB primero; activar backend solo con RPC verificada |
| Colisión de `ticket_code` | Precheck, `UNIQUE`, retry de generación |
| Deadlocks en locks | Orden único: reserva → pasajero; tests concurrentes |
| Consumidores externos desconocidos | Inventario de access logs antes del retiro |
| Crecimiento de `boarding_attempts` | Retención, limpieza e índices acotados |
| Diferencia entre datos históricos y nuevos logs | `state_before/after` nullable; NULL en históricos no demostrables |

## 1. Executive Summary

SEC-009.1 adds **secret scanning** to the Nómadas Tour CI pipeline using `gitleaks/gitleaks-action@v3`. The goal is to block PRs that introduce detected secrets (API keys, JWTs, private keys, etc.) before they reach `main`.

Key design decisions:

| Decision          | Choice                                             | Rationale                                                                                                                                                   |
| ----------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tool              | `gitleaks/gitleaks-action@v3`                      | Selected for existing secret-detection and CI capabilities; GitHub Actions integration; no external service required; Node 24 runtime (Sep 2026 compatible) |
| CI trigger        | `pull_request` + `push → main`                     | Consistent with existing `ci.yml`                                                                                                                           |
| Enforcement       | Required Status Check `secret-scan`                | Blocks merge if scan fails; no code-level gate needed                                                                                                       |
| Permissions       | `contents: read` only                              | Minimum privilege; fork-safe                                                                                                                                |
| PR comments       | **Disabled** (`GITLEAKS_ENABLE_COMMENTS: "false"`) | Avoids `pull-requests: write`; exit code is the enforcement mechanism                                                                                       |
| Baseline          | **Not part of MVP**                                | `gitleaks-baseline.json` does NOT auto-suppress; `--baseline-path` is an explicit CLI flag not used by the action by default                                |
| Pre-commit        | **Excluded**                                       | Not a security enforcement layer; adds friction; CI is the gate                                                                                             |
| `.gitleaksignore` | **Not created**                                    | No concrete need identified; create only if needed post-MVP                                                                                                 |

**Net result:** Any PR that introduces a detected secret pattern will fail the `secret-scan` status check and be blocked from merge by the GitHub Ruleset.

CI scans the Git checkout. Local gitignored `.env*` files are not a technical prerequisite for the scanner to run.

## 2. Repository Findings

### 2.1 `.gitignore` rules

```gitignore
.env*           # line 36 — ignores ALL files starting with .env
backend/.env    # line 37 — explicit ignore for backend real env
```

The `.env*` glob matches `.env`, `.env-example`, `.env-dev-example`, `.env-prod-example`, `.env.local`, and also `backend/.env-example` for **untracked** files (`git check-ignore --no-index backend/.env-example` reports `.gitignore:36:.env*`).

A file that is **already tracked** stays tracked even if it matches `.gitignore`. That is the case for `backend/.env-example`.

### 2.2 Tracked vs. untracked `.env*` files

Classification rule used in this document:

- **Tracked secret → potential Git leak / incident** (rotate and remove from Git).
- **Gitignored local secret → credential sprawl, not a Git leak.** Not an input to CI.

| File                        | Tracked in Git?                                                 | Secrets in Git?                                                                                                                                                                                                            | Classification                                                                                                     |
| --------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `backend/.env-example`      | **Yes** (tracked; `.env*` would ignore it if it were untracked) | **No — placeholders only.** HEAD and introducing commit `120082d` contain `your-supabase-service-role-key`, `your-jwt-secret-min-32-chars`, `re_xxxxxxxx`. `git log -S "eyJhbGci" -- backend/.env-example` has no matches. | **Clean tracked template.** Not a Git leak. No sanitization commit expected unless implementation finds otherwise. |
| `backend/.env`              | No (ignored)                                                    | Not in Git                                                                                                                                                                                                                 | Local secrets if present. Credential sprawl, not a Git leak. Not a CI input.                                       |
| `backend/.env-prod-example` | No (ignored)                                                    | Not in Git                                                                                                                                                                                                                 | If a local copy exists with real values: credential sprawl, not a Git leak. Not a CI input.                        |
| `.env`                      | No (ignored)                                                    | Not in Git                                                                                                                                                                                                                 | Local secrets if present. Credential sprawl, not a Git leak. Not a CI input.                                       |
| `.env-example`              | No (ignored)                                                    | Not in Git                                                                                                                                                                                                                 | Local template only. Hygiene: placeholders. Not a CI input.                                                        |
| `.env-dev-example`          | No (ignored)                                                    | Not in Git                                                                                                                                                                                                                 | If a local copy exists with real values: credential sprawl, not a Git leak. **Critical:** The only tracked `.env*` file is `backend/.env-example`, and its Git content is placeholders. Gitignored local `.env*` files are outside the CI checkout.

Conditional (do not ignore at implementation time):

- If `backend/.env-example` is found **tracked with real credentials**, classify it as a **compromised secret in Git**, remove the values from the tracked file, and rotate the corresponding production credentials.
- If it is tracked with placeholders only (current evidence), it is **clean**.
- If it were not tracked, the table above would be wrong; `git ls-files` currently lists it.

`.github/workflows/ci.yml` — 5 jobs: `security-tests`, `tests`, `backend-tests`, `typecheck`, `build`. All use `actions/checkout@v4`. The new `secret-scan` job will be added alongside these.

### 2.4 Existing security test suites

- `tests/security/` — 19 Vitest tests (JWT forgery, RLS posture, CRITICAL grants, etc.)
- `backend/src/**/*.test.ts` — Backend unit tests (567 tests)
- Root test suite — 399 tests

### 2.5 Git history verification

Evidence gathered for this design (not a substitute for the first full gitleaks scan):

- `git ls-files -- '*env*'` → `backend/.env-example` is tracked.
- Introducing commit: `120082d` (`feat(wkr-007): add trip effects outbox flag`) added `backend/.env-example` with placeholders, not JWTs.
- `git log -S "eyJhbGci" -- backend/.env-example` → no matches.
- `git log --all --diff-filter=A -- '*.env*'` is a **false-negative pathspec** for this filename: `*.env*` does not match `.env-example`. Do not treat a zero result from that command as proof that no env example was ever committed.

**Git-leak conclusion from tracked `.env*` templates:** no secret values were found in `backend/.env-example` history. That is **not** a claim that a full-history scan of every file has already been run.

**CI implication:** MVP does **not** use a baseline. The first `gitleaks` run with `fetch-depth: 0` is the confirmation scan. If it reports **real** historical secrets, that is a Git leak (rotate; do not allowlist). If it reports additional documented false positives, add a **specific** regex or file path — never a directory exclusion.

## 3. Current Secret Exposure Posture

### 3.1 What is committed

| Category                 | Risk                                                                  | Status                                      |
| ------------------------ | --------------------------------------------------------------------- | ------------------------------------------- |
| `backend/.env-example`   | Tracked template. Git content is placeholders, not production secrets | **Clean.** Keep placeholders.               |
| No other `.env*` tracked | —                                                                     | OK                                          |
| Migration SQL files      | No secrets; only schema DDL                                           | OK                                          |
| Test files               | bcrypt fixture hash, fake JWTs, SHA-256 pin — known false positives   | Allowlist individually (regex or file path) |

### 3.2 What is NOT committed (tracked `.env*` templates)

Relative to the tracked env example and the checks in §2.5:

- No real service_role JWTs in `backend/.env-example`
- No real Resend API keys in `backend/.env-example` (`re_xxxxxxxx` is a placeholder)
- No real JWT secret in `backend/.env-example`

This section does **not** assert that gitignored local `.env` files are empty. Those files are not in Git.

### 3.3 Credential sprawl vs. Git leak

| Situation                                   | Label               | CI consequence                                         |
| ------------------------------------------- | ------------------- | ------------------------------------------------------ |
| Secret in a **tracked** file or Git history | Git leak / incident | Scanner must fail until removed; rotate credentials    |
| Secret only in a **gitignored** local file  | Credential sprawl   | Not a Git leak. Not a CI input. Operator hygiene.      |
| Placeholder in a tracked `*.example` file   | Clean template      | May need a narrow allowlist regex if gitleaks flags it |

`backend/.env-prod-example` is gitignored (`git check-ignore` matches `.env*`). It has **never been a Git leak** because it is not in the tracked tree. A local copy with real production values would be **credential sprawl**.

`.gitignore` keeps local `.env*` files out of new commits. CI works on the Git checkout. Sanitizing or deleting gitignored local files is **hygiene / credential-sprawl cleanup**. It is **not** a technical condition for the `secret-scan` job to function.

## 5. Gitleaks Configuration Design

### 5.1 `.gitleaks.toml` — Minimal configuration

The configuration **extends the built-in Gitleaks rules** (`[extend] useDefault = true`) instead of replacing them. It declares a **single** `[[allowlists]]` table with **one** `regexes` array and **one** `paths` array. No custom detection rules. **No directory exclusions.** Do not use the legacy `[allowlist]` table.

`[extend] useDefault = true` is required so built-in rules stay active. A config that only contains `[[allowlists]]` (without `useDefault = true`) would otherwise replace the default rules.

```toml
title = "Nómadas Tour — Gitleaks configuration"

[extend]
useDefault = true

[[allowlists]]
description = "Global allowlist for verified false positives"

regexes = [
  '''ci-anon-key-not-a-secret''',
  '''your-supabase-service-role-key''',
  '''your-jwt-secret-min-32-chars''',
  '''re_xxxxxxxx''',
  '''test-service-role''',
  '''test-jwt-secret''',
  '''test-resend''',
  '''\$2a\$10\$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy''',
  '''firma_invalida''',
]

paths = [
  '''tests/boarding/wkr-007\.2\.test\.ts''',
]
```

Do not declare `regexes` or `paths` more than once inside `[[allowlists]]`. Repeated keys are invalid TOML for this purpose.

### 5.2 Allowlist strategy

Applied in this order of preference:

1. **Specific regex** (most precise) — placeholder strings, test-only values, the known bcrypt fixture hash, `firma_invalida`
2. **Specific file path** (moderate precision) — one test file with a documented SHA-256 migration pin
3. **Directory exclusion** — **not used in SEC-009.1.** Never exclude a directory entirely.

`supabase/tests/` is scanned. Known bcrypt fixtures are allowlisted by the exact hash regex above. New content added under `supabase/tests/` remains visible to gitleaks.

**Never allowlisted:**

- Real service_role JWTs
- Real Resend API keys
- Real AWS keys
- GitHub tokens
- Private keys
- Real DB credentials
- Real JWT secrets
- Production anon keys
- Broad patterns such as `eyJ.*` or a generic `JWT` token matcher

### 5.3 Verified false positives

This table is the allowlist source of truth. It must match §5.1 and §8.

| File                                 | Finding                                                                         | Why false positive                                     | Allowlist mechanism                                      |
| ------------------------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------- |
| `.github/workflows/ci.yml`           | `ci-anon-key-not-a-secret`                                                      | Placeholder string, not a real key                     | regex `ci-anon-key-not-a-secret`                         |
| `tests/boarding/wkr-007.2.test.ts`   | SHA-256 hash `21d94032345b9aa142a428e6605a28d86af86aa4e9f2c19650a9a99435b3a550` | Migration pin hash — deterministic, documented         | path `tests/boarding/wkr-007\.2\.test\.ts`               |
| `supabase/tests/*.sql`               | bcrypt `$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy`           | SQL test fixture (known test vector), not a credential | regex of that exact hash — **not** a directory exclusion |
| `backend/src/*.test.ts`              | `test-service-role`, `test-jwt-secret`, `test-resend`                           | Test-only values, clearly labeled                      | those three regexes                                      |
| `backend/.env-example`               | `your-supabase-service-role-key`, `your-jwt-secret-min-32-chars`, `re_xxxxxxxx` | Placeholder strings already in the tracked template    | those three regexes                                      |
| `docs/security-audit-remediation.md` | JWT example ending in `firma_invalida`                                          | Documented invalid-signature example, not a real token | regex `firma_invalida` — **not** `eyJ.*`                 |

Not included in the allowlist:

- `your-resend-api-key` — planned placeholder string that does **not** appear in the tracked file. The tracked Resend placeholder is `re_xxxxxxxx`.
- Path `supabase/tests/` — would hide new secrets added to that directory.

## 6. PR/CI Architecture

### 6.1 Job specification

```yaml
secret-scan:
  name: secret-scan
  runs-on: ubuntu-latest
  timeout-minutes: 5
  permissions:
    contents: read
  steps:
    - name: Checkout
      uses: actions/checkout@v6
      with:
        fetch-depth: 0

    - name: Gitleaks scan
      uses: gitleaks/gitleaks-action@v3
      env:
        GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        GITLEAKS_ENABLE_COMMENTS: "false"
```

### 6.2 Key design decisions

| Decision                      | Value                         | Rationale                                                                                                                                |
| ----------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `fetch-depth: 0`              | Full clone                    | Gitleaks needs git history to detect secrets across commits                                                                              |
| `timeout-minutes: 5`          | Short timeout                 | Gitleaks scans are fast; prevents hung jobs                                                                                              |
| `GITHUB_TOKEN`                | `${{ secrets.GITHUB_TOKEN }}` | Required by action for API calls; auto-provided by GitHub; not a production secret                                                       |
| `GITLEAKS_ENABLE_COMMENTS`    | `"false"`                     | Prevents action from calling `pulls-create-review-comment` API (requires `pull-requests: write`). Exit code is the enforcement mechanism |
| `permissions: contents: read` | Minimum privilege             | Sufficient for checkout + scan; fork-safe                                                                                                |
| `GITLEAKS_LICENSE`            | **Omitted**                   | Not required for free-tier use                                                                                                           |

### 6.3 Required Status Check

The `secret-scan` job must be added as a **Required Status Check** in the GitHub Ruleset for `main`:

- Ruleset → Branch protection → `main`
- Add `secret-scan` to "Require status checks to pass"
- PRs that fail the gitleaks scan will be blocked from merge

This is configured in the GitHub UI, not in code.

### 6.4 What is NOT used

| Not used                          | Why                                                                                                 |
| --------------------------------- | --------------------------------------------------------------------------------------------------- |
| `pull_request_target`             | Would run in context of base branch with write access — security risk; `pull_request` is sufficient |
| `pull-requests: write`            | Not needed when PR comments are disabled                                                            |
| `security-events: write`          | Not needed — no SARIF upload in MVP                                                                 |
| Production secrets                | Never exposed to CI; gitleaks scans source code only                                                |
| Custom `GITHUB_TOKEN` permissions | Default `secrets.GITHUB_TOKEN` with `contents: read` is sufficient                                  |
| Local gitignored `.env*` files    | Not in the checkout; sanitizing them is not required for the job to run                             |

## 7. Permissions and Fork Security Model

### 7.1 GitHub Token permissions

The `GITHUB_TOKEN` is auto-generated by GitHub Actions for each workflow run. With `permissions: contents: read`, it has:

- **Read** access to repository contents
- **No write** access to repository contents
- **No PR comment** access (would require `pull-requests: write`)

### 7.2 Why `GITLEAKS_ENABLE_COMMENTS: "false"`

The gitleaks-action uses the `GITHUB_TOKEN` to call the GitHub Pull Request Review Comment API (`POST /repos/{owner}/{repo}/pulls/{pull_number}/comments`). This API requires `pull-requests: write` permission.

By setting `GITLEAKS_ENABLE_COMMENTS: "false"`:

- The action does NOT call the PR comments API
- `contents: read` is sufficient
- The action's **exit code** (0 = pass, non-zero = fail) is the enforcement mechanism
- The Required Status Check `secret-scan` blocks merge when the exit code is non-zero

**PR comments are informational convenience, not a security enforcement mechanism.** They can be enabled in a future follow-up by adding `pull-requests: write` to the job permissions.

### 7.3 Fork safety

With `pull_request` (not `pull_request_target`) and `contents: read`:

- Fork PRs run with the **fork's token** (limited permissions)
- No access to repository secrets (other than `GITHUB_TOKEN` which is read-only)
- No write access to the repository
- Safe for external contributors

### 7.4 Production secret isolation

No production secrets are used by the `secret-scan` job:

- `GITHUB_TOKEN` is auto-generated, not a production secret
- Gitleaks scans **source code** for detected patterns; it does not need database credentials, API keys, or JWTs to function
- The scan result is independent of any secret value
- Gitignored local `.env` files are not checked out and are not required to exist on the runner

## 8. Allowlist Policy

### 8.1 Principles

1. **Specific regex > specific file path > directory exclusion** (in order of preference)
2. **Never exclude a directory entirely** in SEC-009.1
3. **Never allowlist a real secret** — only known false positives and placeholders
4. **Prefer global allowlist** in `.gitleaks.toml` over per-file overrides
5. **Minimize allowlist surface** — each entry must be justified by a verified false positive
6. **One `regexes` array and one `paths` array** in a single `[[allowlists]]` table. Do not use `[allowlist]`.

### 8.2 Global allowlist entries (`regexes`)

| Pattern                                                           | Type  | Justification                                                                                      |
| ----------------------------------------------------------------- | ----- | -------------------------------------------------------------------------------------------------- |
| `ci-anon-key-not-a-secret`                                        | Regex | CI env placeholder in `ci.yml`; never a real key                                                   |
| `your-supabase-service-role-key`                                  | Regex | Placeholder in tracked `backend/.env-example`                                                      |
| `your-jwt-secret-min-32-chars`                                    | Regex | Placeholder in tracked `backend/.env-example`                                                      |
| `re_xxxxxxxx`                                                     | Regex | Resend placeholder in tracked `backend/.env-example`                                               |
| `test-service-role`                                               | Regex | Test-only value in backend test files                                                              |
| `test-jwt-secret`                                                 | Regex | Test-only value in backend test files                                                              |
| `test-resend`                                                     | Regex | Test-only value in backend test files                                                              |
| `\$2a\$10\$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy` | Regex | Known bcrypt fixture in `supabase/tests/*.sql`. New hashes in that directory are **not** excluded. |
| `firma_invalida`                                                  | Regex | Invalid JWT signature example in `docs/security-audit-remediation.md`. Do not use `eyJ.*`.         |

### 8.3 Path-based allowlist entries (`paths`)

| Path                                  | Justification                                         |
| ------------------------------------- | ----------------------------------------------------- |
| `tests/boarding/wkr-007\.2\.test\.ts` | SHA-256 migration pin hash; deterministic, documented |

There is **no** path entry for `supabase/tests/`.

### 8.4 What is NOT allowlisted

- Real service_role JWTs (even if found in test data)
- Real Resend API keys (even if used in tests)
- Real AWS keys
- GitHub tokens (real or format-matching)
- Private keys (PEM files, SSH keys)
- Real DB credentials or connection strings
- `backend/.env` real values (gitignored, not in the CI checkout; would be flagged if committed)
- The directory `supabase/tests/`
- Broad JWT patterns (`eyJ.*`, generic `JWT` matchers)
- Any pattern that matches a production secret format

### 8.5 `.gitleaksignore`

**Not created in this ticket.** The `.gitleaksignore` file (similar to `.gitignore` for gitleaks) is only warranted if post-implementation reveals specific findings that cannot be resolved by allowlisting. It should be used as a last resort, not a first response.

## 9. Local Developer Workflow

### 9.1 Local scanning (feedback only, not enforcement)

Developers can run gitleaks locally for fast feedback:

```powershell
# Scan entire repo (with redacted output to avoid displaying found secrets)
gitleaks git --redact .

# Scan only staged changes (pre-commit check)
gitleaks protect --staged --redact
```

Local scans still follow Git (tracked files and history). They do not depend on sanitizing gitignored `.env*` files, except that a developer who force-adds a `.env` would then be scanning that secret.

### 9.2 What is NOT implemented

| Not implemented         | Why                                                                        |
| ----------------------- | -------------------------------------------------------------------------- |
| Husky pre-commit hook   | Not an enforcement layer; CI is the gate; adds friction for all developers |
| lint-staged integration | Not needed for secret scanning; gitleaks scans full repo                   |
| npm install gitleaks    | Gitleaks is a Go binary, not an npm package; local install is optional     |

### 9.3 Developer expectations

- If a PR fails the `secret-scan` check, the developer must investigate and fix before requesting review
- Local `gitleaks git --redact .` can be used to reproduce the CI scan locally
- False positives should be added to `.gitleaks.toml` allowlist with justification (specific regex or specific file path; never a whole directory)

## 10. Historical Scan / Baseline — Post-MVP

### 10.1 Current state

`gitleaks-baseline.json` does NOT exist in the repository and is NOT part of this MVP.

### 10.2 How baseline actually works

**Common misconception:** The mere presence of `gitleaks-baseline.json` in the repository causes gitleaks to automatically suppress known findings.

**Actual behavior:** `gitleaks-baseline.json` is an optional file that can be passed to gitleaks via the `--baseline-path` flag:

```bash
gitleaks git --baseline-path gitleaks-baseline.json .
```

When this flag is provided, gitleaks compares current findings against the baseline and **only reports new findings** that are NOT in the baseline. Without the flag, the baseline file has no effect.

**The `gitleaks-action@v3` does NOT auto-detect or auto-apply baseline files.** The action runs `gitleaks git` / `gitleaks protect` without `--baseline-path` by default.

### 10.3 Post-MVP path

If a historical scan of the full repo reveals findings that cannot be resolved (test fixtures, documentation, etc.):

1. Run `gitleaks git --redact .` locally
2. Review each finding; add resolvable false positives to `.gitleaks.toml` allowlist (specific regex or specific file)
3. For truly unresolvable findings, create `gitleaks-baseline.json`
4. Pass `--baseline-path gitleaks-baseline.json` in the action configuration
5. Document the baseline in the allowlist justification

Real historical secrets are **not** “unresolvable findings.” They are a Git leak: remove/rotate. Do not baseline them in SEC-009.1.

This baseline workflow is a separate future task, not part of SEC-009.1.

## 11. Credential Sprawl / `.env*` Policy

### 11.1 Policy

```text
.gitignore evita que los .env locales entren al repositorio.
CI trabaja sobre el checkout de Git.
```

Local `.env*` files are **not a vault**. Credentials should be:

- Stored in provider dashboards (Supabase, Render, Resend)
- Optionally stored in a personal secret manager (out of scope for this ticket)
- Never committed to Git (enforced by `.gitignore` for untracked `.env*`)
- Placeholders only in any example file that **is** tracked

### 11.2 Tracked template (CI-relevant)

#### `backend/.env-example` (tracked)

**Git state (verified):** placeholders.

```text
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_SERVICE_ROLE_KEY=your-supabase-service-role-key
JWT_SECRET=your-jwt-secret-min-32-chars
RESEND_API_KEY=re_xxxxxxxx
```

**SEC-009.1 action:** verify this remains true. Do **not** treat a sanitization edit as a required CI step unless implementation finds real values in the tracked file or in Git history.

If real values are found in Git: classify as a Git leak, replace with placeholders, and rotate.

### 11.3 Gitignored local files (hygiene only — not a CI gate)

These files are not in the Git checkout. The `secret-scan` job does not need them to be sanitized, present, or absent.

| File                        | Git     | Operator hygiene if a local copy exists                                     |
| --------------------------- | ------- | --------------------------------------------------------------------------- |
| `.env`                      | ignored | Keep local; never `git add -f`                                              |
| `backend/.env`              | ignored | Keep local; never `git add -f`                                              |
| `.env-example`              | ignored | Placeholders only if the file is used as a template                         |
| `.env-dev-example`          | ignored | Placeholders only if recreated                                              |
| `backend/.env-prod-example` | ignored | Placeholders only if recreated; real prod values here are credential sprawl |

Cleaning local copies is **credential-sprawl cleanup**. It is not part of the Definition of Done for the CI scanner.

### 11.4 Rotation policy

**Not part of this ticket as a CI task.**

- **Git leak** (secret in tracked history): rotate the leaked credential. SEC-009.1 must not allowlist it.
- **Credential sprawl** (secret only in a gitignored local file): rotation is an operator decision, not a scanner prerequisite.

| 3   | Remove temp file                            | PASS (exit 0)                                   |
| 4   | All allowlist entries are valid patterns    | PASS (exit 0)                                   |
| 5   | PR with detected secret                     | `secret-scan` status check FAILS; merge blocked |

### 12.2 What is NOT tested

- No Vitest tests for gitleaks (gitleaks is an external binary, not a JS module)
- No test framework integration
- No mock scanning
- No snapshot testing of scan results

### 12.3 CI validation

The `secret-scan` job itself is validated by:

1. Committing the CI workflow change
2. Opening a PR
3. Confirming the `secret-scan` job runs and passes on the clean repo
4. Optionally creating a temp fixture to confirm it fails (then removing the fixture before merge)

## 14. Implementation Sequence

### Step 1: Verify tracked env template (not a local-hygiene gate)

1. Confirm `git ls-files -- backend/.env-example` lists the file
2. Confirm Git content is placeholders (`your-supabase-service-role-key`, `your-jwt-secret-min-32-chars`, `re_xxxxxxxx`)
3. If real credentials are present in Git, stop and treat as a Git leak (placeholders + rotation). Do not proceed by allowlisting them
4. Do **not** block this ticket on sanitizing gitignored local `.env*` files

### Step 2: Create gitleaks configuration

1. Create `.gitleaks.toml` with `[extend] useDefault = true` and the single `[[allowlists]]` from §5.1 / §8
2. Verify TOML has one `[[allowlists]]` table, one `regexes` array, and one `paths` array. Do not use `[allowlist]`.
3. Verify `supabase/tests/` is not in `paths`
4. Verify path `tests/boarding/wkr-007\.2\.test\.ts` (not `wkr-007.test.ts`)
5. Verify no real secrets are in the file

### Step 3: Update CI workflow

1. Add `secret-scan` job to `.github/workflows/ci.yml`
2. Position as the first job (fail fast — secrets check before expensive builds)
3. Keep existing jobs unchanged
4. `permissions: contents: read` and `GITLEAKS_ENABLE_COMMENTS: "false"`

### Step 4: Update documentation

1. Update `TASKS.md` with SEC-009.1 entry
2. Update `docs/ROADMAP.md` with SEC-009.1 status
3. Update `docs/SEC-009-continuous-security-validation-design.md` to reference SEC-009.1

### Step 5: Validate

1. `git diff --check` — no whitespace errors
2. `npx.cmd prettier --check docs/SEC-009.1-secret-scanning-implementation-design.md`
3. `git diff --stat` — confirm only intended files changed
4. Verify no real secrets in tracked files
5. Verify `.gitleaks.toml` is syntactically valid
6. Verify `ci.yml` is valid YAML
7. `gitleaks git --redact .` on the checkout (does not require local `.env` sanitization)

### Step 6: Post-implementation (manual)

1. Configure Required Status Check `secret-scan` in GitHub Ruleset
2. Open PR and verify `secret-scan` job runs and passes
3. Optionally test false-positive scenario (create fixture → fail → remove)

## 15. Risks / Mitigations

| Risk                                             | Likelihood  | Impact                           | Mitigation                                                                               |
| ------------------------------------------------ | ----------- | -------------------------------- | ---------------------------------------------------------------------------------------- |
| False positive on legitimate code                | Medium      | Medium (blocks PR)               | Allowlist entry in `.gitleaks.toml`; requires justification                              |
| Gitleaks-action v3 breaking change               | Low         | High (CI fails)                  | Pin to specific SHA if needed; monitor release notes                                     |
| Node 20 deprecation (Sep 2026)                   | None for v3 | None                             | v3 uses Node 24; compatible                                                              |
| New secret pattern not caught by gitleaks        | Low         | High (secret in code)            | Gitleaks built-in rules are comprehensive; review periodically                           |
| Baseline auto-application misunderstanding       | Medium      | Medium (false sense of security) | This document explicitly clarifies baseline does NOT auto-apply                          |
| Developer bypasses CI with direct push to `main` | Low         | High                             | Branch protection ruleset requires status check; direct push to `main` is blocked        |
| Allowlist entry too broad                        | Low         | Medium (missed real secret)      | Allowlist entries are specific regexes, not broad patterns; review during implementation |
| Directory exclusion of `supabase/tests/`         | —           | High (hidden new secrets)        | Not used. Bcrypt fixtures use an exact-hash regex                                        |
| Treating local `.env` cleanup as a CI gate       | Medium      | Low (wasted work / false deps)   | CI scans Git checkout only                                                               |

## Appendix A: Quick Reference — Key Corrections Applied

| Misconception                                                                    | Corrected fact                                                                                                                   |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| "`gitleaks-baseline.json` auto-suppresses findings"                              | No. The file has no effect unless explicitly passed via `--baseline-path` CLI flag. The action does NOT use this flag by default |
| "`GITLEAKS_LICENSE` is needed for v3"                                            | Not required for free-tier / personal use                                                                                        |
| "v3 uses Node 20"                                                                | v3 uses Node 24; Node 20 deprecation is Sep 16, 2026                                                                             |
| "`permissions: contents: read` enables PR comments"                              | No. PR comments require `pull-requests: write`. With `contents: read` only, set `GITLEAKS_ENABLE_COMMENTS: "false"`              |
| "`backend/.env-example` contains real prod secrets **and** there is no incident" | Incompatible. Tracked file currently has placeholders → clean. If it had real secrets, it would be a Git leak                    |
| "`.env-prod-example` is a Git leak"                                              | No. It is gitignored and not tracked. Real values in a local copy would be credential sprawl, not a leak                         |
| "`*.env*` git log of 0 commits means no env file was committed"                  | False negative pathspec. `backend/.env-example` was added in `120082d` with placeholders                                         |
| "Exclude `supabase/tests/` because of bcrypt"                                    | No. Use the exact fixture-hash regex so new files in that directory are still scanned                                            |
| "JWT doc example needs a path allowlist or `eyJ.*`"                              | No. Use `firma_invalida`                                                                                                         |
| "Local `.env` sanitization is required for CI"                                   | No. `.gitignore` keeps local `.env` out of Git. CI scans the checkout                                                            |
| "Pre-commit hooks are enforcement"                                               | No. CI is the enforcement layer; pre-commit is convenience only                                                                  |
| "Allowlist `regexes`/`paths` may be repeated keys"                               | No. One `[[allowlists]]` table with one `regexes` array and one `paths` array. Do not use `[allowlist]`                          |
| "SEC-009.1 depends on future Gitleaks feature development"                       | No. `gitleaks/gitleaks-action@v3` is selected for existing secret-detection and CI capabilities                                  |
| "A `.gitleaks.toml` allowlist replaces built-in rules"                           | No. `[extend] useDefault = true` extends the built-in Gitleaks rules                                                             |
| "Test file is `wkr-007.test.ts`"                                                 | No. The file is `tests/boarding/wkr-007.2.test.ts`                                                                               |

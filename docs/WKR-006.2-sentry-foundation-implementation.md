## Objetivo

Integración base de Sentry (`@sentry/node`) en API y worker como capa de observabilidad opcional.  
No cambia negocio, outbox, contratos ni ADR-001.

---

---

## Decisiones

1. Un solo wrapper — el resto del código no importa `@sentry/node`.
2. `SENTRY_ENABLED=false` (default) → no-op total; comportamiento idéntico al pre-Sentry.
3. Sin Performance / Replay / Frontend / Profiling.
4. No reportar 401/403/404/409/422/400 ni requeues/skips/completed.
5. Fingerprints estables: `api/http/...`, `worker/<name>/<area>/<handler>`.
6. PII scrub en tags/context + `beforeSend` (sin body/cookies/auth).
7. Logs/métricas/heartbeat WKR-006.1 intactos.

## Variables de entorno

| Variable | Default | Descripción |
|----------|---------|-------------|
| `SENTRY_ENABLED` | `false` | Master switch |
| `SENTRY_DSN` | `""` | DSN; vacío = no init aunque enabled |
| `SENTRY_ENVIRONMENT` | `NODE_ENV` | `development` / `staging` / `production` |
| `SENTRY_RELEASE` | `npm_package_version` o `1.0.0` | Release tag |

---

## Cómo habilitar

```bash
# backend/.env (API y worker)
SENTRY_ENABLED=true
SENTRY_DSN=https://<key>@o<org>.ingest.sentry.io/<project>
SENTRY_ENVIRONMENT=staging
SENTRY_RELEASE=1.0.0
```

Reiniciar API (`npm run dev` / `start`) y worker (`npm run worker`).

## Cómo deshabilitar

```bash
SENTRY_ENABLED=false
# o omitir SENTRY_DSN
```

El sistema opera igual que antes de WKR-006.2.

## Qué se captura

| Superficie | Captura |
|------------|---------|
| API uncaught / unhandledRejection | Sí |
| API errorHandler non-AppError / AppError ≥500 | Sí |
| API 401–422 / ValidationError | No |
| Worker uncaught / unhandled / fatal | Sí |
| Relay loop / recovery RPC errors | Sí |
| Handler exception → max attempts | Sí |
| no_handler | Sí |
| Requeue / skip / completed / settle | No |
| Permanent domain failed (log only) | No |

---

## Cómo validar

1. Con `SENTRY_ENABLED=false`: suites verdes; worker procesa outbox; logs iguales.
2. Con enabled + DSN de staging: forzar un `throw` 500 en una ruta de prueba temporal (o error de cleanup) y verificar evento con tags `service`, `environment`, `release`.
3. Confirmar que un 404 de API **no** aparece en Sentry.
4. Confirmar que `flags_not_settled` requeues **no** aparecen en Sentry.

---

## Riesgos

| Riesgo | Mitigación |
|--------|------------|
| Cuota Free | Default off; filtros de ruido |
| PII | Scrub + no payloads |
| Ruido retries | Solo max_attempts / infra |
| Flush en crash | `flushSentry` antes de exit |

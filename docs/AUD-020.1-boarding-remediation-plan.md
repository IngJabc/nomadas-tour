# AUD-020.1 — Plan de remediación del sistema de boarding

**Tipo:** Plan técnico de implementación futura  
**Fecha:** 2026-08-04  
**Estado:** Propuesto — no implementado  
**Origen:** [AUD-020 — Boarding cross-agency](AUD-020-boarding-cross-agency.md)  
**Decisión normativa:** [ADR-001 — Boarding cross-agency](decisions/ADR-001-boarding-cross-agency.md)

> Este documento no implementa cambios. Define el alcance, el orden y los
> contratos que deberá seguir una remediación posterior.

---

## 1. Resumen ejecutivo

El flujo vigente de boarding por pasajero individual es:

```text
lookupPassengerByQR
        ↓
toggleBoarding
```

Este flujo respeta ADR-001: `reservation.agency_id` representa propiedad
comercial y `trip_agencies` representa autorización operacional del viaje.

La remediación debe consolidar esta implementación como único flujo, retirar
tres endpoints legacy, hacer la transición atómica e idempotente, reemplazar la
búsqueda parcial por dos identificadores exactos, reducir PII y fortalecer la
auditoría. El estado de boarding continuará perteneciendo al pasajero, no al
asiento.

La operación crítica se encapsulará en una RPC transaccional
`boarding_toggle()`, definida como `SECURITY DEFINER` y ejecutable únicamente
por `service_role`. Esta decisión crea una frontera controlada de dominio, pero
no sustituye la autorización por `trip_agencies`.

---

## 2. Objetivos

### Objetivos funcionales

1. Mantener boarding cross-agency conforme a ADR-001.
2. Exponer un único flujo de lookup y transición por pasajero.
3. Garantizar una sola transición y un solo log bajo concurrencia.
4. Hacer board/unboard idempotentes respecto al estado solicitado.
5. Permitir lookup exacto mediante código corto o QR completo.
6. Entregar al scanner únicamente la información operacional necesaria.
7. Separar eventos reales de boarding de intentos operacionales.
8. Derivar el estado visual de abordaje sin mutar `seats.status`.

### Objetivos de seguridad

- Mantener identidad y tenant desde el contexto confiable del backend.
- Autorizar operación mediante `trip_agencies`.
- Evitar búsqueda arbitraria y enumeración por fragmentos.
- Restringir la RPC a `service_role`.
- No almacenar el QR completo en telemetría de intentos.
- Atribuir cada acción al usuario y agencia operadora.

### Fuera de alcance

- Cambiar la decisión cross-agency.
- Crear un portal de pasajeros.
- Convertir boarding en una operación comercial de la reserva.
- Dar acceso directo a la RPC a `anon` o `authenticated`.
- Introducir `seat.status = 'boarded'`.
- Rediseñar otros flujos de reservas.

## 3. Decisiones de producto y arquitectura

### 3.1 Fronteras de dominio

```text
reservation.agency_id
        │
        └── ownership comercial

trip_agencies
        │
        └── autorización operacional del viaje
```

- Solo la agencia propietaria administra comercialmente la reserva.
- Cualquier agencia asignada al viaje puede operar boarding de sus pasajeros.
- El permiso operacional no habilita CRUD, métricas ni listados comerciales
  externos.

### 3.2 Flujo único

Permanecen conceptualmente:

```text
lookupPassengerByQR
        ↓
toggleBoarding
        ↓
boarding_toggle()
```

Se eliminan las rutas y métodos legacy descritos en H1.

### 3.3 `SECURITY DEFINER`

`boarding_toggle()` se definirá como:

```sql
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
```

La función no necesita `SECURITY DEFINER` para obtener atomicidad; esta proviene
de la transacción PostgreSQL y de los locks `FOR UPDATE`. Se adopta como
frontera controlada para una operación crítica y para no depender del rol
llamador que pueda usar el backend en el futuro.

La migración que cree la función deberá ejecutar, en la misma unidad de cambio:

```sql
REVOKE EXECUTE ON FUNCTION public.boarding_toggle(...) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION public.boarding_toggle(...) FROM anon;
REVOKE EXECUTE ON FUNCTION public.boarding_toggle(...) FROM authenticated;
GRANT EXECUTE ON FUNCTION public.boarding_toggle(...) TO service_role;
```

Requisitos adicionales:

- propietario conocido y controlado;
- referencias de tablas y funciones calificadas con schema;
- sin SQL dinámico;
- parámetros tipados;
- sin confiar en valores de `user_metadata`;
- actor y agencia recibidos desde el contexto validado del backend;
- validación interna de membresía en `trip_agencies`;
- validación de que el actor pertenece a la agencia operadora;
- tests de grants y de ejecución denegada para roles cliente.

`SECURITY DEFINER` no convierte una llamada en autorizada. La función debe
rechazar cualquier operación donde la agencia no esté asignada al viaje.

### 3.4 Estado de boarding

La fuente de verdad es:

```text
reservation_passengers.boarded
reservation_passengers.boarded_at
```

`seats.status` continuará representando disponibilidad, lock, reserva o bloqueo
operacional del puesto. El estado visual “abordado” se deriva combinando el
puesto reservado con el pasajero asociado.

## 4. Arquitectura objetivo

### 4.1 Lookup

```text
Scanner
  │
  ├── código corto exacto
  └── QR completo exacto
          ↓
POST /agency/boarding/lookup
          ↓
lookupPassengerByQR
          ├── normalizar entrada
          ├── resolver ticket_code o qr_code por igualdad
          ├── validar trip_agencies + estado + departure_time
          ├── registrar intento sin QR en claro
          └── devolver BoardingLookupDTO mínimo
```

Se recomienda `POST` con body para evitar que el QR quede en URLs, access logs,
historial o métricas de proxy. El nombre de servicio puede conservarse aunque
el endpoint cambie de método.

### 4.2 Transición

```text
PATCH /agency/boarding/:passengerId
          ↓
toggleBoarding
          ↓
RPC boarding_toggle(
  passenger_id,
  requested_boarded,
  actor_user_id,
  operator_agency_id
)
          ↓
transacción PostgreSQL
  1. localizar reserva
  2. bloquear reserva FOR UPDATE
  3. bloquear pasajero FOR UPDATE
  4. validar actor, agencia, viaje, reserva y pasajero
  5. comparar estado actual con estado solicitado
  6. actualizar solo si existe transición
  7. recalcular estado agregado de la reserva
  8. insertar boarding_logs solo si changed=true
  9. devolver resultado estructurado
```

Bloquear solo el pasajero no basta: dos pasajeros distintos de la misma reserva
podrían recalcular `reservations.status` al mismo tiempo. El lock de la reserva
serializa el agregado. Todas las operaciones deben adquirir locks en el mismo
orden para evitar deadlocks.

### 4.3 Resultado de transición

Contrato mínimo:

```ts
interface BoardingToggleResult {
  passenger_id: string;
  boarded: boolean;
  boarded_at: string | null;
  changed: boolean;
  reservation_status: 'confirmed' | 'partial' | 'completed';
  boarded_count: number;
  total_count: number;
}
```

## 5. Hallazgos y remediaciones

### H1 — Flujo legacy duplicado

#### Retirar

Endpoints:

```text
POST /agency/reservations/board
POST /agency/scanner/board
POST /agency/scanner/lookup
```

Backend:

```text
boardPassenger
boardPassengers
lookupReservationByQR
```

Frontend:

```text
agencyApi.boardPassenger()
```

También deben eliminarse schemas, controllers, imports y tipos que queden sin
uso.

#### Criterio

- No queda ninguna ruta HTTP alternativa de boarding.
- No queda lógica que filtre boarding por `reservation.agency_id`.
- El scanner continúa usando exclusivamente lookup individual y toggle.
- Antes del retiro se confirma que no existen consumidores externos conocidos;
  si los hubiera, se anuncia el cambio como breaking change.

### H2 — Atomicidad

Crear `public.boarding_toggle()` en una migración futura.

Responsabilidades transaccionales:

1. Obtener y bloquear la reserva y el pasajero.
2. Comprobar que el actor existe, está activo y pertenece a la agencia
   operadora.
3. Comprobar que el pasajero está activo.
4. Comprobar que la reserva no está cancelada.
5. Comprobar que el viaje está activo, ya salió y no está cancelado,
   completado ni archivado.
6. Comprobar la asignación `(trip_id, operator_agency_id)` en
   `trip_agencies`.
7. Aplicar la transición, si corresponde.
8. Recalcular `reservations.status` usando pasajeros activos.
9. Insertar el evento real en `boarding_logs`.
10. Retornar el estado confirmado por la base de datos.

La actualización del pasajero, el agregado de la reserva y el log deben hacer
commit o rollback juntos.

### H3 — Idempotencia

La operación expresa estado deseado, no “alternar” ciegamente:

| Estado actual | Estado solicitado | Resultado |
|---------------|-------------------|-----------|
| `false` | `true` | `changed=true`, fija `boarded_at`, log `board` |
| `true` | `false` | `changed=true`, limpia `boarded_at`, log `unboard` |
| `true` | `true` | `changed=false`, conserva `boarded_at`, sin log |
| `false` | `false` | `changed=false`, conserva `boarded_at`, sin log |

Los casos `changed=false` retornan success. No deben producir `409`, actualizar
timestamps ni emitir un evento de boarding real.

### H4 — Búsqueda manual exacta

#### Código corto

```text
input = 6BBD52E9
WHERE ticket_code = input
```

#### QR completo

```text
input = NT-LA OLLA-6BBD52E983AB495493EAEE20466C18A2
WHERE qr_code = input
```

Reglas:

- `trim` y normalización a mayúsculas antes de consultar;
- código corto con formato estricto de 8 caracteres hexadecimales;
- igualdad exacta mediante `.eq()`;
- `ticket_code` y `qr_code` con constraints de unicidad;
- sin fallback parcial;
- sin `ILIKE`, comodines ni búsqueda por destino;
- cero resultados para `6BBD`, `BBD52`, `495493` o `LA OLLA`;
- máximo un resultado por identificador;
- aplicar el mismo guard operacional antes de devolver datos.

#### Persistencia de `ticket_code`

Una migración futura deberá:

1. agregar `reservations.ticket_code`;
2. hacer backfill desde el identificador aleatorio final del QR existente;
3. detectar y resolver colisiones antes de agregar unicidad;
4. agregar `CHECK` de ocho caracteres hexadecimales en mayúsculas;
5. agregar constraint o índice `UNIQUE`;
6. convertir la columna a `NOT NULL` cuando el backfill esté validado;
7. actualizar `create_agency_reservation` para generarlo y retornarlo.

La generación debe manejar colisiones explícitamente; ocho caracteres
hexadecimales no garantizan unicidad por sí solos.

### H5 — Reducción de PII

Definir un DTO exclusivo de boarding. No reutilizar DTOs administrativos.

```ts
interface BoardingLookupDTO {
  trip: {
    id: string;
    status: string;
    departure_time: string;
    route: {
      origin: string;
      destination: string;
    };
  };
  reservation_status: string;
  reservation_agency_name: string;
  passengers: Array<{
    id: string;
    name: string;
    seat_code: string | null;
    boarded: boolean;
    boarded_at: string | null;
  }>;
}
```

Eliminar del lookup:

- `passenger.document`;
- `booker_document`;
- teléfonos;
- `qr_code`;
- datos comerciales o de contacto no necesarios.

El nombre del pasajero se conserva por decisión operacional. El frontend no
debe mantener tipos o renderers para los campos retirados.

### H6 — Auditoría

#### `boarding_logs`

Continuará siendo el registro autoritativo de transiciones reales. Agregar:

```text
trip_id
reservation_agency_id
state_before
state_after
```

Requisitos:

- backfill de filas existentes cuando la relación todavía pueda resolverse;
- FK e índices para viaje y agencia propietaria;
- `state_before` y `state_after` coherentes con `action`;
- inserción dentro de la misma transacción de `boarding_toggle()`;
- ninguna fila para operaciones idempotentes sin cambio.

#### `boarding_attempts`

Crear una tabla separada para intentos de:

```text
lookup
board
unboard
```

Campos mínimos propuestos:

```text
id
attempted_at
actor_user_id
operator_agency_id
trip_id nullable
reservation_id nullable
reservation_passenger_id nullable
operation
outcome
failure_code nullable
credential_hash nullable
```

Reglas:

- `outcome` diferencia success, no_change, denied, not_found y error;
- no almacenar QR, código corto, documentos, teléfonos ni payload completo;
- para lookup exitoso, guardar `sha256(qr_code)` calculado en servidor;
- para lookup fallido, guardar solo hash SHA-256 de la entrada normalizada;
- insertar únicamente desde backend/service role;
- no publicar en Realtime por defecto;
- definir retención y purga antes de habilitar la tabla en producción;
- un fallo de telemetría no debe crear una transición parcial.

`boarding_logs` es consistencia de negocio; `boarding_attempts` es trazabilidad
de intentos. No deben mezclarse.

Los errores esperados de dominio pueden devolverse como resultado estructurado
o registrarse desde el backend después del rechazo. No se debe intentar guardar
un intento fallido dentro de una transacción que luego se abortará, porque ese
registro también haría rollback.

### H7 — Estado visual de asientos

Eliminar cualquier mutación que use boarding para cambiar `seats.status`.

Modelo visual:

```text
seat.status
      +
reservation_passenger.boarded
      ↓
visualSeatStatus
```

Prioridad visual propuesta:

1. pasajero abordado → `boarded`;
2. pasajero reservado no abordado → `reserved`;
3. lock vigente → `locked`;
4. bloqueo operacional → `blocked`;
5. sin asignación → `available`.

`boarded` puede seguir existiendo como variante visual de `Seat`, pero no como
valor persistido de `seats.status`.

### H8 — Cobertura de tests

La suite debe cubrir contratos, servicios, función SQL y concurrencia. El
detalle se define en la sección 8.

## 7. Cambios esperados en base de datos

### 7.1 `reservations`

- Nueva columna `ticket_code`.
- Backfill verificado.
- Formato hexadecimal de ocho caracteres.
- Unicidad e índice para lookup exacto.
- Generación incluida en el flujo transaccional de creación de reserva.

### 7.2 `boarding_toggle()`

Firma conceptual:

```text
boarding_toggle(
  p_passenger_id UUID,
  p_boarded BOOLEAN,
  p_actor_user_id UUID,
  p_operator_agency_id UUID
) RETURNS boarding toggle result
```

Debe bloquear, validar, actualizar, recalcular y auditar en una sola
transacción. La función será `SECURITY DEFINER`, con permisos exclusivos para
`service_role`.

### 7.3 `boarding_logs`

- Agregar viaje, agencia propietaria y transición antes/después.
- Backfill e índices.
- Mantener actor, agencia operadora, pasajero, acción y fecha.
- Insertar únicamente cuando `changed=true`.

### 7.4 `boarding_attempts`

- Nueva tabla de telemetría operacional sin credenciales en claro.
- Escritura exclusiva del backend.
- Índices por fecha, agencia, viaje, operación y resultado.
- Política de retención explícita.
- Sin publicación Realtime salvo una necesidad futura aprobada.

### 7.5 RLS y grants

- La RPC no será ejecutable por roles cliente.
- `service_role` será el único rol con `EXECUTE`.
- Las tablas de auditoría no tendrán escritura directa de `anon` o
  `authenticated`.
- No es necesario ampliar RLS de pasajeros para ejecutar boarding mientras la
  única entrada sea el backend.
- Cualquier futura lectura cross-agency por JWT requerirá una decisión y
  policies específicas basadas en `trip_agencies`; no debe habilitarse de forma
  implícita en esta remediación.

## 8. Estrategia de tests

### 8.1 Tests de caracterización — antes de retirar legacy

- Confirmar que el frontend usa únicamente lookup/toggle individual.
- Confirmar que `agencyApi.boardPassenger` no tiene consumidores.
- Capturar el contrato vigente que debe mantenerse para la pantalla scanner.
- Confirmar que retirar endpoints legacy no rompe imports ni rutas activas.

### 8.2 Autorización

| Caso | Resultado esperado |
|------|--------------------|
| Agencia propietaria asignada al viaje | Permitido |
| Agencia externa asignada al mismo viaje | Permitido |
| Agencia no asignada | 403 / error de dominio |
| Actor que no pertenece a la agencia operadora | Rechazado |
| Viaje futuro | Rechazado |
| Viaje cancelado, completado o archivado | Rechazado |

### 8.3 Lookup

| Entrada | Resultado |
|---------|-----------|
| `6BBD52E9` | Match exacto por `ticket_code` |
| QR completo | Match exacto por `qr_code` |
| `6BBD` | Sin resultados |
| `BBD52` | Sin resultados |
| `495493` | Sin resultados |
| `LA OLLA` | Sin resultados |
| Código de viaje no asignado | Rechazado/sin contexto operacional |

Aserciones de privacidad:

- respuesta sin `passenger.document`;
- respuesta sin `booker_document`;
- respuesta sin teléfonos;
- respuesta sin QR completo;
- intento persistido sin credencial en claro.

### 8.4 Boarding

- `false → true`: actualiza pasajero, fija `boarded_at`, recalcula reserva y
  crea un log.
- `true → false`: limpia `boarded_at`, recalcula reserva y crea un log.
- `true → true`: success, `changed=false`, conserva timestamp y no crea log.
- `false → false`: success, `changed=false` y no crea log.
- pasajero cancelado: rechazado sin cambios.
- reserva cancelada: rechazada sin cambios.
- recálculo correcto para `confirmed`, `partial` y `completed`.
- rollback completo si falla la inserción del log.
- `seats.status` permanece sin cambios.

### 8.5 Concurrencia

Tests de integración reales, no mocks:

1. Dos `board=true` simultáneos sobre el mismo pasajero:
   - ambas respuestas exitosas;
   - una con `changed=true`;
   - una con `changed=false`;
   - un solo `boarding_logs`.
2. Board y unboard simultáneos:
   - ejecución serializada;
   - estado final coincide con el orden confirmado por la DB;
   - un log por cada transición real, en orden.
3. Boarding simultáneo de dos pasajeros de una reserva:
   - estado agregado final correcto;
   - sin estado perdido;
   - conteos consistentes.

### 8.6 Seguridad de función

- `PUBLIC`, `anon` y `authenticated` no pueden ejecutar la RPC.
- `service_role` puede ejecutarla.
- `search_path` y propietario coinciden con lo esperado.
- IDs manipulados no evitan validación de actor/agencia/viaje.
- No existen grants implícitos posteriores a recrear la función.

### 8.7 Regresión visual

- Puesto reservado no abordado mantiene visual de reservado.
- Puesto cuyo pasajero está abordado usa visual de abordado.
- Unboarding restaura visual reservado, no disponible.
- Locks y bloqueos operacionales conservan su semántica.
- Layouts Kia y bus no cambian su distribución física.

## 9. Riesgos y mitigaciones

| Riesgo | Mitigación |
|--------|------------|
| Consumidor externo usa endpoint legacy | Inventario de tráfico y comunicación de breaking change antes del retiro |
| Colisión de `ticket_code` | Constraint UNIQUE, precheck de backfill y retry de generación |
| Deadlock por locks inconsistentes | Orden único: reserva → pasajero; tests concurrentes |
| Divergencia entre guard backend y RPC | Tabla compartida de casos y tests contractuales en ambas capas |
| Escalada por `SECURITY DEFINER` | Grants mínimos, schemas calificados, sin SQL dinámico, validación interna |
| QR expuesto en URL o logs | Lookup POST y hash; nunca persistir texto completo en attempts |
| Crecimiento de `boarding_attempts` | Índices limitados, retención y limpieza programada |
| Telemetría impide operación | Separar attempts de la transacción crítica; alertar sin dejar boarding parcial |
| Despliegue backend antes de migración | Publicar DB primero y activar backend después de verificar RPC |
| Rollback revive flujo legacy | Rollback compatible con versión previa controlada, sin mantener dos flujos activos indefinidamente |

## 10. Orden de implementación

### P0 — Tests base y contratos

1. Agregar tests de caracterización del scanner actual.
2. Tipar DTO de lookup y resultado de toggle.
3. Agregar tests de autorización cross-agency y PII.
4. Preparar entorno de integración PostgreSQL para concurrencia.

**Gate:** suite base estable antes de eliminar código.

### P1 — Retiro del flujo legacy

1. Confirmar ausencia de consumidores internos y externos.
2. Eliminar las tres rutas.
3. Eliminar controllers, schemas y servicios legacy.
4. Eliminar `agencyApi.boardPassenger`.
5. Verificar que scanner conserva lookup/toggle individual.

**Gate:** una sola superficie HTTP de boarding.

### P2 — `boarding_toggle()`

1. Crear migración incremental.
2. Implementar locks, validaciones, idempotencia y agregado.
3. Restringir ejecución a `service_role`.
4. Cambiar `toggleBoarding` para invocar la RPC.
5. Ejecutar tests de rollback y concurrencia.

**Gate:** una transición y un log bajo doble scan.

### P3 — Contrato de lookup exacto

1. Agregar y poblar `ticket_code`.
2. Aplicar constraints e índices.
3. Actualizar creación de reservas.
4. Reemplazar `ILIKE` por igualdad exacta.
5. Migrar lookup a POST.
6. Probar código corto, QR completo y fragmentos.

**Gate:** ningún fragmento arbitrario produce resultados.

### P4 — Auditoría y reducción de PII

1. Aplicar DTO mínimo.
2. Ampliar `boarding_logs`.
3. Crear `boarding_attempts`.
4. Implementar hashing y outcomes.
5. Definir retención.

**Gate:** respuestas y tablas de intentos sin PII/QR innecesarios.

### P5 — Corrección visual de asientos

1. Eliminar mutaciones de seats asociadas a boarding.
2. Derivar visual de abordado desde pasajero + puesto.
3. Validar layouts y estados.

**Gate:** boarding no altera disponibilidad persistida del asiento.

### P6 — Suite final y despliegue

1. Ejecutar unitarios, integración, seguridad y frontend.
2. Validar grants en la base aplicada.
3. Hacer smoke test con dos agencias del mismo viaje.
4. Verificar telemetría y ausencia de datos sensibles.
5. Actualizar documentación operativa después del despliegue.

## 11. Criterios de aceptación

### Dominio

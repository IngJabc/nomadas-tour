# AUD-020.12 — Realtime cross-agency boarding visibility

**Tipo:** Auditoría + fix de visibilidad Realtime  
**Fecha:** 2026-08-05  
**Estado:** Implemented (RLS fix on `boarding_logs`)  
**ADR-001:** Intacta — ownership comercial vs autorización operacional sin cambios  

---

## 1. Comportamiento reproducido

Viaje con Agencia A y Agencia B asignadas. Reserva comercialmente de **Agencia A**.

| Caso | DB / RPC | Realtime receptor |
|------|----------|-------------------|
| B aborda pasajero de reserva A | ✅ correcto | A recibe ✅ |
| A aborda pasajero de su reserva | ✅ correcto | B **no** recibe ❌ |

Conclusión: boarding cross-agency OK; falla solo la **entrega Realtime al no-dueño**.

---

## 2. Flujo actual

```
boarding_toggle (service_role)
  → UPDATE reservation_passengers (boarded)
  → UPDATE reservations (status)
  → INSERT boarding_logs (trip_id, reservation_agency_id, …)
       ↓
supabase_realtime publication
       ↓
Cliente scanner: subscribeToBoardingLogs(..., tripId)
       ↓
RLS SELECT boarding_logs  →  ¿fila visible para el JWT?
       ↓
Si sí → evento → lookupByQR silent refetch
Si no → silencio (UI desactualizada)
```

Tabla origen del evento para el scanner: **`boarding_logs`** (INSERT), no `seats`.

---

## 3. Causa encontrada (confirmada)

### 3.1 RLS — ownership comercial

Políticas vigentes (039) para SELECT de agencia:

| Tabla | Condición SELECT |
|-------|------------------|
| `reservations` | `agency_id = private.auth_app_agency_id()` |
| `reservation_passengers` | `reservation_id ∈ reservations` del dueño |
| `boarding_logs` | `reservation_id ∈ reservations` del dueño |

Identidad: `private.auth_app_role()` / `private.auth_app_agency_id()` desde `public.users` + `auth.uid()`.  
**No** usan `auth.jwt()` claims de rol ni `user_metadata`.  
**No** usan `trip_agencies` para lectura de boarding.

Realtime aplica esas policies → solo el **dueño comercial** recibe eventos de `boarding_logs` / `reservation_passengers` de esa reserva.

Eso explica:

- B aborda → log de reserva de A → A (dueña) recibe ✅  
- A aborda → mismo log → B (asignada, no dueña) **no** puede SELECT → no evento ❌  

### 3.2 Frontend — filtro correcto por trip

Scanner (`app/agency/scan/page.tsx`):

```ts
subscribeToBoardingLogs(callback, tripId); // filter: trip_id=eq.<trip>
```

El canal escucha por **`trip_id`**, no por `agency_id`. El bug **no** es el filtro del cliente; es RLS que descarta el evento antes de entregarlo.

`useTripRealtime` (admin) escucha `reservation_passengers` sin filtro de agencia; admin usa policy superadmin → no afectado.

`subscribeToReservations(agencyId)` filtra por ownership a propósito (lista comercial); fuera del path de boarding live del scanner.

## 5. Diseño del fix

Nueva migración: `048_boarding_logs_trip_agency_realtime_read.sql`

Ampliar **solo** `bl_agency_read`:

Una agencia puede SELECT `boarding_logs` si:

1. es dueña comercial de la reserva (**existente**), **o**
2. `boarding_logs.trip_id` está en `trip_agencies` para su `agency_id` (**nuevo**)

Mantener:

- aislamiento entre viajes (via `trip_agencies.trip_id`)
- agencia no asignada → sin eventos
- sin `auth.jwt()` / `user_metadata`
- sin abrir SELECT global de `reservation_passengers`
- INSERT de logs sigue vía RPC `service_role` (`bl_agency_insert` sin cambio funcional requerido)

Impacto de datos en el evento: metadatos de boarding (acción, seat_ids, agencies, trip).  
No incluye `booker_document` / documentos de pasajero. El scanner refetch usa API backend (DTO mínimo).

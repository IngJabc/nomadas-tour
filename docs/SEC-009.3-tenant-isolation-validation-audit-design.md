## 1. Executive Verdict

**DESIGN READY WITH OBSERVATIONS**

The repository has a mature, defense-in-depth tenant isolation architecture (RLS + middleware + service-role RPCs). Existing tests cover application-layer auth and domain logic well, but **no automated real-DB RLS regression suite exists**. The primary blocker is validating Supabase CLI feasibility for ephemeral CI databases and determining the exact mechanism to reproduce authenticated RLS context.

**Implementation may begin only after the SEC-009.3 feasibility spike passes.**

**Next step:** `SEC-009.3-SP1 — Supabase Local CI Feasibility Spike`

## 3. Verified Repository Facts

### 3.1 Database Architecture (72 migrations applied)

| Aspect               | Verified State                                                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Tenant-scoped tables | 20 tables with `agency_id` or `tenant_id`                                                                                          |
| RLS enabled          | **100% of tables** — operational tables deny-all (RLS enabled, no policies)                                                        |
| Auth helpers         | `private.auth_app_role()` / `private.auth_app_agency_id()` — STABLE SECURITY DEFINER, grants to `authenticated` + `service_role`   |
| Mutation path        | **All INSERT/UPDATE/DELETE revoked from `authenticated`/`anon`** — 20+ SECURITY DEFINER RPCs granted exclusively to `service_role` |
| Realtime             | 11 tables published; delivery = RLS SELECT visibility                                                                              |
| Audit log            | `agency_id` nullable (NULL = system/superadmin); append-only trigger + single writer `audit_append`                                |
| Public/tokenized     | Reservation links via token; `public_get/save_reservation_link` RPCs; no table SELECT for anon                                     |

### 3.2 Backend Authorization Stack

| Layer             | Mechanism                                                          | Coverage                        |
| ----------------- | ------------------------------------------------------------------ | ------------------------------- |
| Auth middleware   | `auth.ts` → JWT → `supabase.auth.getUser()` → fetch `public.users` | All `/api/*`                    |
| Role middleware   | `authorize('agency' \| 'superadmin')`                              | `/api/agency/*`, `/api/admin/*` |
| Tenant middleware | `tenant.ts` → agency status + ownership                            | `/api/agency/*` only            |
| Service layer     | Explicit `trip_agencies` checks before every operation             | All agency controllers          |
| RPC calls         | `supabaseAdmin.rpc(...)` — re-validates at DB level                | All mutations                   |

**Critical invariant**: Agency ID **never** comes from client — always from `req.ctx.agencyId` (set by middleware from DB, not JWT).

## 5. Threat Model

### 5.1 Read Attacks

| Target                        | Agency A Attempts                                             | Expected Result               |
| ----------------------------- | ------------------------------------------------------------- | ----------------------------- |
| Reservations (B)              | `SELECT * FROM reservations WHERE agency_id = B`              | 0 rows (RLS)                  |
| Passengers (B)                | JOIN via reservation                                          | 0 rows / denied               |
| Seats (B's trip)              | `SELECT * FROM seats WHERE trip_id IN (...)`                  | Allowed (public RLS)          |
| Boarding logs (B commercial)  | `SELECT * FROM boarding_logs WHERE reservation_agency_id = B` | 0 rows (RLS)                  |
| Boarding logs (B operational) | `SELECT * FROM boarding_logs WHERE trip_id = shared`          | Rows returned (dual-path RLS) |
| Audit records (B)             | `SELECT * FROM audit_log WHERE agency_id = B`                 | 0 rows (RLS)                  |
| Reservation links (B)         | `SELECT * FROM reservation_links WHERE agency_id = B`         | 0 rows (RLS)                  |
| Notifications (B)             | `SELECT * FROM notifications WHERE agency_id = B`             | 0 rows (RLS)                  |
| Realtime (B)                  | Subscribe to B's reservation/boarding channels                | No events delivered           |

### 5.2 Write Attacks

| Target                                  | Agency A Attempts                | Expected Result                           |
| --------------------------------------- | -------------------------------- | ----------------------------------------- |
| Create reservation with `agency_id = B` | RPC `create_agency_reservation`  | Denied (RPC validates `req.ctx.agencyId`) |
| Update B's reservation                  | RPC `cancel_agency_reservation`  | Denied (RPC ownership check)              |
| Delete B's reservation                  | DELETE via RPC                   | Denied (no DELETE RPC for agencies)       |
| Modify B's seats                        | RPC `lock/unlock`                | Denied (trip_agencies check)              |
| Manipulate B's boarding                 | RPC `boarding_toggle`            | Denied (operator not assigned)            |
| Modify B's reservation links            | RPC `create/confirm/cancel_link` | Denied (link ownership)                   |

### 5.3 RPC Attacks

| RPC                             | Agency A Invokes For B              | Expected Result                  |
| ------------------------------- | ----------------------------------- | -------------------------------- |
| `create_agency_reservation`     | Trip assigned to B, not A           | `TRIP_NOT_ASSIGNED`              |
| `cancel_agency_reservation`     | Reservation owned by B              | `FORBIDDEN` / `NOT_FOUND`        |
| `boarding_toggle`               | Passenger on trip A not assigned to | `FORBIDDEN` (trip_agencies)      |
| `create_reservation_link`       | Trip assigned to B, not A           | `TRIP_NOT_ASSIGNED`              |
| `update_agency_branding`        | Agency B                            | `FORBIDDEN` (agency_id mismatch) |
| Trip RPCs (`create_trip`, etc.) | Any                                 | `FORBIDDEN` (superadmin only)    |

### 5.4 Identity Attacks

| Vector                                     | Assessment                                                                                 |
| ------------------------------------------ | ------------------------------------------------------------------------------------------ |
| Forged JWT `user_metadata.role=superadmin` | **Blocked** — backend reads `public.users`, not JWT metadata                               |
| Forged JWT `user_metadata.agency_id=B`     | **Blocked** — middleware fetches real `users.agency_id`                                    |
| Valid user with wrong agency               | **Blocked** — middleware re-queries `users` table                                          |
| Service role key leak                      | **Mitigated** — gitleaks CI (`secret-scan`) + deny-all client grants                       |
| Helper hijacking (`private.auth_app_*`)    | **Blocked** — STABLE SECURITY DEFINER, `search_path=public`, EXECUTE only to trusted roles |

## 7. Three Authorization Layers — Explicit Separation

The design validates **each layer independently**:

| Layer                            | Question                                                 | Test Method                                                   |
| -------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------- |
| **A. DB / RLS**                  | Can authenticated Agency A read/modify B's row directly? | SQL executed under **authenticated actor subject to RLS**     |
| **B. RPC Authorization**         | Can Agency A invoke privileged RPC for B's resources?    | RPC called under **authenticated actor**; asserts error codes |
| **C. Backend/API Authorization** | Can Agency A traverse HTTP + middleware + service for B? | HTTP requests with **Agency A JWT**; asserts HTTP status      |

**No layer substitutes for another.** A backend test that mocks the DB does not prove RLS. An RLS test that uses `service_role` does not prove RLS works.

## 8. RLS Context Reproduction Strategy

### Problem

RLS policies depend on:

```sql
private.auth_app_role()     -- returns 'agency' | 'superadmin' from public.users
private.auth_app_agency_id() -- returns agency_id from public.users
```

These helpers read `public.users` where `id = auth.uid()`.

### Required Test Context

To reproduce a real authenticated session in PostgreSQL:

```sql
-- 1. Create test users in auth.users + public.users (fixture setup, service_role)
INSERT INTO auth.users (id, email, encrypted_password, role, email_confirmed_at) VALUES
  ('aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa', 'a@test.com', '...', 'authenticated', now()),
  ('bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb', 'b@test.com', '...', 'authenticated', now());

INSERT INTO public.users (id, email, role, agency_id, full_name) VALUES
  ('aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa', 'a@test.com', 'agency', 'aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa', 'Agency A Admin'),
  ('bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb', 'b@test.com', 'agency', 'bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb', 'Agency B Admin');

-- 2. Execute isolation query as authenticated actor
SET ROLE authenticated;
SET LOCAL request.jwt.claims = '{"sub": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa", "role": "authenticated"}';
SELECT * FROM reservations WHERE agency_id = 'bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb';
-- Must return 0 rows
```

### Mechanism Status

| Component                      | Status                                                                                     |
| ------------------------------ | ------------------------------------------------------------------------------------------ |
| `SET ROLE authenticated`       | **VERIFIED** — works in Postgres                                                           |
| `SET LOCAL request.jwt.claims` | **SPIKE REQUIRED** — must verify exact behavior with current Supabase/PostgREST version    |
| `auth.uid()` resolution        | **SPIKE REQUIRED** — must confirm it reads from `request.jwt.claims.sub` in local stack    |
| `private.auth_app_agency_id()` | **SPIKE REQUIRED** — must confirm it reads `public.users` for `auth.uid()` under test role |

**The spike (SEC-009.3-SP1) must validate this exact chain works end-to-end.**

### Fixture Setup (service_role)

- Create agencies, users, trips, seats, reservations, passengers, links
- Use `service_role` (bypasses RLS) for all test data creation/cleanup
- **Isolation queries NEVER use service_role**

| Condition                                                   | Test                       |
| ----------------------------------------------------------- | -------------------------- |

| Agency A NOT assigned, reads boarding logs commercial path  | 0 rows / 403               |
| Agency A NOT assigned, subscribes to boarding logs realtime | No events                  |

### PII Protection

- `boarding_logs` does **not** contain passenger documents/contacts
- `reservation_passengers` never exposed cross-agency (RLS enforces commercial owner only)
- Verify: boarding response never includes PII from `reservation_passengers`

## 12. Public / Tokenized Boundary (Reservation Links)

### Tenant-Critical Invariants (In Scope)

| Test                                                        | Assertion                                                            |
| ----------------------------------------------------------- | -------------------------------------------------------------------- |
| Token valid → returns link data for link's agency only      | Response `agency_id` = link's agency                                 |

### Out of Scope (Future / Other Tickets)

- Token enumeration resistance
- Rate-limit abuse testing
- Security fuzzing of public endpoints
- General public API hardening

## 16. CI Architecture (MVP)

### Job: `tenant-isolation` (added to existing `.github/workflows/ci.yml`)

```yaml
tenant-isolation:
  name: tenant-isolation
  runs-on: ubuntu-latest
  timeout-minutes: 15
  permissions:
    contents: read
  steps:
    - name: Checkout
      uses: actions/checkout@v4

    - name: Setup Node
      uses: actions/setup-node@v4
      with:
        node-version: ${{ env.NODE_VERSION }}
        cache: npm

    - name: Install Supabase CLI (pinned)
      run: |
        curl -fsSL https://github.com/supabase/cli/releases/download/v1.XX.X/supabase_linux_amd64.tar.gz | tar -xz
        echo "$(pwd)" >> $GITHUB_PATH
      # Version pinned in script above

    - name: Start Supabase Local
      run: supabase start
      env:
        SUPABASE_TELEMETRY_DISABLED: "true"

    - name: Install root dependencies
      run: npm ci

    - name: Install backend dependencies
      run: npm ci --prefix backend

    - name: Run tenant isolation tests
      run: npm run test:tenant:ci
      env:
        SUPABASE_URL: http://127.0.0.1:54321
        SUPABASE_SERVICE_ROLE_KEY: ${{ secrets.SUPABASE_SERVICE_ROLE_KEY_LOCAL }}
        SUPABASE_ANON_KEY: ${{ secrets.SUPABASE_ANON_KEY_LOCAL }}

    - name: Stop Supabase
      if: always()
      run: supabase stop
```

### Key Design Decisions

| Decision    | Value                  | Rationale                                            |
| ----------- | ---------------------- | ---------------------------------------------------- |
| Job name    | `tenant-isolation`     | Matches `secret-scan` / `dependency-scan` convention |
| Leaf job    | No `needs:`            | Parallel with other jobs                             |
| Realtime    | Not started            | Faster, less flaky; nightly covers it                |
| Timeout     | 15 min                 | Migrations + tests                                   |
| Permissions | `contents: read`       | Minimum privilege                                    |
| CLI version | Pinned in install step | Reproducible; no `latest`                            |

**Local credentials**: Supabase local generates its own keys on `start`. If the action needs them, they can be captured from stdout or the local config. **No GitHub Secrets required** for local stack.

## 21. Risks / Mitigations

| Risk                                  | Severity | Mitigation                                                                             |
| ------------------------------------- | -------- | -------------------------------------------------------------------------------------- |
| Supabase CLI flakiness in CI          | High     | Spike first; pin CLI version; retry logic; fallback to staging if local fails          |
| Docker not available / slow           | Medium   | GitHub `ubuntu-latest` has Docker pre-installed; cache images                          |
| Migrations fail to apply cleanly      | High     | `supabase db reset` validates locally first                                            |
| Realtime tests flaky                  | Medium   | Excluded from PR CI; nightly only                                                      |
| Seed drift vs migrations              | Medium   | Seed SQL versioned with migrations; `supabase db reset` includes seed                  |
| CI runtime > 15 min                   | Medium   | Optimize: parallel test files, minimal seed, cache                                     |
| Test user JWT expiration              | Low      | Use `SET ROLE authenticated` + JWT claims for DB tests; short-lived JWTs for API tests |
| Cross-agency boarding false positives | Medium   | Explicit positive + negative tests; document ADR-001 exception                         |
| Staging coupling (future)             | Low      | Nightly optional; PR CI fully independent                                              |
